Section 26 — Scenario-Based Interview Questions

React • 3–5 Years Experience • Practical Engineering Judgment

How to Answer Scenario Questions

Problem ↓ Reproduce ↓ Measure / collect evidence ↓ Find root cause ↓ Choose smallest safe fix ↓ Validate ↓ Monitor

At 3–5 years, interviewers usually want to see how you think, not just which API you remember.

Strong answer pattern: "First I would measure and isolate the problem. Then I would identify the root cause, choose a targeted fix, validate it with metrics/tests, and consider the trade-offs."

1. A Component Re-renders 500 Times. How Do You Debug It?

Answer: First reproduce the issue and use React DevTools Profiler to identify which component is rendering and what triggered it. Then inspect state updates, parent renders, Context changes and unstable object/function props. I would look for effects that update state repeatedly, changing dependencies and unnecessary derived state. I would fix the root cause before adding memoization.
Profiler ↓ Which component? ↓ Why did it render? ├── Parent ├── State ├── Context └── Props ↓ Fix source ↓ Measure again 
// Suspicious effect
useEffect(() => {
  setData({ ...data });
}, [data]); // creates a new object → update → effect → loop

2. Your App Becomes Slow After Adding Redux. What Investigate?

Answer: I would not assume Redux itself is the problem. I would profile renders and inspect selectors, subscriptions, large store updates and state placement. I would check whether components subscribe to a large slice when they need only one field, whether reducers create unnecessary new references, and whether frequently changing UI state was moved into global state unnecessarily.
  • React Profiler.
  • Redux DevTools.
  • Selector granularity.
  • Large/normalized state.
  • Unnecessary global UI state.

3. A List of 50,000 Items Freezes the UI. How Optimize?

Answer: I would avoid rendering all 50,000 DOM nodes. First I would virtualize the list. If the dataset is remote, I would also use server-side pagination/cursor fetching. Then I would profile row rendering and reduce unnecessary calculations/re-renders.
50,000 records ↓ Server pagination/cursor ↓ Visible subset ↓ Virtualized rendering ↓ ~visible rows only
Do not solve a large-list problem by simply adding React.memo to every row. Rendering fewer rows is usually the bigger win.

4. API Requests Fire Twice in Development. Why?

Answer: In React development with StrictMode, effects can be intentionally re-run through extra setup/cleanup checks. This can expose code that is not resilient to remounting. I would make the effect correctly clean up and make the request logic safe rather than disabling StrictMode just to hide the symptom.
useEffect(() => {
  const controller = new AbortController();

  fetch("/api/users", {
    signal: controller.signal
  });

  return () => controller.abort();
}, []);

Also verify that the duplicate call is actually from StrictMode and not from changing dependencies, multiple component instances or an accidental render/effect loop.

5. How Would You Implement Optimistic Updates?

Answer: Update the UI immediately, send the mutation, then confirm the result. If the server rejects it, restore the previous state and show an error. I would also consider whether the operation is safe to perform optimistically and how concurrent changes are reconciled.
User action ↓ Save previous state ↓ Update UI immediately ↓ API mutation ├── Success → Confirm/invalidate └── Failure → Rollback + error

6. How Would You Prevent Duplicate API Calls?

Answer: It depends on why the duplicate occurs. I would first identify whether it comes from multiple renders, StrictMode, repeated clicks, duplicate component instances or concurrent requests. Then I would use the appropriate solution: request deduplication/cache, disabled submission state, AbortController, a query library, or server-side idempotency for critical mutations.
ProblemPossible solution
Repeated GETCache/query deduplication.
Double submitDisable/guard + server idempotency.
Stale requestAbort/cancel or ignore stale result.
Multiple consumersShared server-state cache.

7. Cancel an In-flight Request When a Component Unmounts

Answer: Use AbortController and abort the request during effect cleanup. Also handle AbortError separately so normal cancellation is not treated as a real application error.
useEffect(() => {
  const controller = new AbortController();

  async function load() {
    try {
      const response = await fetch("/api/data", {
        signal: controller.signal
      });

      const data = await response.json();
      setData(data);
    } catch (error) {
      if (error.name !== "AbortError") {
        setError(error);
      }
    }
  }

  load();

  return () => controller.abort();
}, []);

8. How Would You Implement RBAC?

Answer: Keep authorization decisions on the server. The frontend can use user roles/permissions to hide or disable UI and protect routes for user experience, but it must never be the final security boundary.
User ↓ Authentication ↓ Session + permissions ↓ Frontend ├── Hide/disable UI └── Route guards + Backend ↓ Authoritative authorization 
const canEdit =
  permissions.includes("project:edit");
Critical: Never trust a hidden button as authorization.

9. How Would You Design a Reusable Data Table?

Answer: Separate the table engine from feature-specific data. Define a column configuration, stable row IDs, sorting/filtering models, pagination and selection. For large datasets, support server-side operations and virtualization. Keep cell rendering extensible.
DataTable ├── Columns config ├── Header ├── Filters ├── Virtualized rows ├── Selection ├── Pagination └── Cell renderers ↓ Feature data/API

10. How Would You Implement Dark Mode Across an Application?

Answer: Use semantic design tokens/CSS variables rather than hardcoding colors inside components. Keep the selected theme at an application-level boundary, persist the preference if needed, and initialize it early enough to reduce theme flashing.
:root {
  --bg: #ffffff;
  --text: #111827;
}

[data-theme="dark"] {
  --bg: #111827;
  --text: #f9fafb;
}

body {
  background: var(--bg);
  color: var(--text);
}

11. How Would You Share State Between Unrelated Components?

Answer: First identify whether the state is actually shared client state or server state. For small local sharing, lift state to a common parent. For distant components, Context or a state store can be appropriate. For server data, use a server-state/cache solution rather than treating API data as ordinary global state.
Avoid globalizing state simply because prop drilling is inconvenient. Choose the smallest appropriate ownership boundary.

12. How Would You Implement Offline Support?

Answer: Define what should work offline first. Cache important read data locally, persist drafts, queue supported mutations and synchronize when connectivity returns. For collaborative or conflicting data, define conflict-resolution rules.
Online ↓ API + local cache ↓ Offline ↓ Local reads / queued writes ↓ Network restored ↓ Sync ↓ Resolve conflicts

13. How Would You Optimize a Dashboard with Multiple Charts?

Answer: Treat each widget independently. Fetch/cache data per widget, render independent loading/error states, lazy-load heavy charting code and avoid rendering charts that are not visible. I would profile chart rendering and reduce unnecessary updates.
  • Independent queries.
  • Shared server-state cache.
  • Code splitting for heavy charts.
  • Visibility-based rendering where useful.
  • Memoization only after profiling.

14. How Would You Manage Forms with 100+ Fields?

Answer: Avoid making the entire form re-render on every keystroke. Use a form library with efficient subscriptions, keep field components isolated, use schema-driven validation and consider sections/virtualization for very large forms.
Large Form ├── Section A ├── Section B ├── Section C └── Section D ↓ Field-level subscriptions ↓ Only affected fields update

15. How Would You Migrate a Large React Application Incrementally?

Answer: Avoid a big-bang rewrite. First define boundaries and target architecture, then migrate feature by feature. Keep old and new implementations interoperable, add tests around critical behavior, and measure each migration.
Legacy app ↓ Boundary ↓ Migrate Feature A ↓ Migrate Feature B ↓ Migrate Feature C ↓ Remove legacy boundary

16. How Would You Handle Feature Flags?

Answer: Centralize flag evaluation and keep flags typed/documented. Decide whether each flag is build-time or runtime. For important releases, support gradual rollout and quick rollback. Remove temporary flags after the feature is stable.
if (flags.newDashboard) {
  return <NewDashboard />;
}

return <OldDashboard />;
Feature flags are temporary architecture. Unused flags should not remain forever.

17. How Would You Structure a Monorepo with Shared UI Components?

Answer: Separate applications and reusable packages with clear dependency boundaries.
repo/
├── apps/
│   ├── admin/
│   └── customer/
├── packages/
│   ├── ui/
│   ├── eslint-config/
│   ├── tsconfig/
│   └── utils/
└── package.json

The shared UI package should contain reusable primitives, while business-specific components should remain in the relevant application/feature package.

18. How Would You Debug a Memory Leak in React?

Answer: Reproduce the issue and use browser memory tools and React profiling. Look for effects that leave event listeners, timers, subscriptions, observers or sockets active. Check whether objects remain referenced after unmount and verify cleanup.
useEffect(() => {
  const handler = () => {};
  window.addEventListener("resize", handler);

  return () => {
    window.removeEventListener("resize", handler);
  };
}, []);
A growing heap is not automatically a leak. Confirm retained objects and repeated growth over controlled cycles.

19. How Would You Ensure Accessibility in a Complex Form?

Answer: Start with semantic HTML and native controls. Give every field an accessible name, connect errors to inputs, preserve logical keyboard order, manage focus after validation/step changes, and test with keyboard and screen-reader tooling.
<label htmlFor="email">Email</label>
<input
  id="email"
  aria-describedby="email-error"
  aria-invalid={!!error}
/>
{error && (
  <p id="email-error">{error}</p>
)}

20. How Would You Profile and Reduce Bundle Size?

Answer: Measure the production bundle first using a bundle analyzer and inspect which dependencies/chunks are large. Then remove unnecessary dependencies, improve imports, enable tree shaking, split heavy routes/features and lazy-load non-critical code. Finally verify the result with performance metrics.
Build ↓ Bundle analyzer ↓ Find largest chunks ↓ Dependency analysis ↓ Tree shaking / splitting / lazy loading ↓ Rebuild ↓ Measure again

22. Most Important Follow-up Questions

  1. How would you measure whether your solution improved performance?
  2. What happens if the API fails?
  3. What happens if the user clicks twice?
  4. What happens if the network disconnects?
  5. What happens when the component unmounts?
  6. How does this scale to 100,000 records?
  7. How would you test this?
  8. What is the accessibility behavior?
  9. What happens if two users modify the same data?
  10. How would you roll back a bad deployment?
  11. What state belongs locally and what belongs globally?
  12. What would you cache?
  13. What would you lazy-load?
  14. What would you monitor in production?
  15. What trade-off did you make?
