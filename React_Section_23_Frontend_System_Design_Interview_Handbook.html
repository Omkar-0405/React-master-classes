Section 23 — Frontend System Design

Simple Interview Handbook • React • Architecture • State • Data • Performance • Scalability

1. What is Frontend System Design?

Frontend system design is the process of deciding how a large UI should be structured so it remains understandable, fast, reliable and easy to extend.

Requirements ↓ Architecture ↓ Components + State ↓ Data/API layer ↓ Caching + Error handling ↓ Performance + Scalability ↓ Monitoring + Testing
Interview rule: Do not start by drawing 20 components. First clarify requirements, users, scale, data, interactions and constraints.

2. A Simple Interview Framework

  1. Clarify requirements — functional + non-functional.
  2. Define scale — users, records, requests, update frequency.
  3. Sketch architecture — UI, state, API/data, cache.
  4. Decompose components — page → feature → reusable components.
  5. Define state placement — local, shared, server/cache, URL.
  6. Define data flow — where data enters and who owns it.
  7. Handle loading/error/empty states.
  8. Discuss performance — virtualization, memoization, code splitting.
  9. Discuss reliability — retries, optimistic updates, offline strategy.
  10. Discuss extensibility — plugins, configuration, design system.

3. Generic Frontend Architecture

4. State Placement

The most important question is: "Who needs this state?"

StateGood location
Input valueComponent/local form state.
Modal open/closedNearest common component.
ThemeContext/provider or app-level state.
Current filtersLocal state or URL search params if shareable.
API responseServer-state/cache layer.
Authentication sessionApp-level auth/session mechanism.
Global notification queueShared store/provider.
Avoid putting everything in Redux/global state. Keep state as close as practical to the components that own and use it.

5. State Categories

Application state ├── Local UI state │ └── modal, input, dropdown ├── Shared client state │ └── selected workspace, preferences ├── Server state │ └── users, orders, projects ├── URL state │ └── filters, page, search └── Persistent state └── settings, drafts, offline data

6. Data Flow

API ↓ Query / Data layer ↓ Cache ↓ Feature container ↓ Presentational components ↓ User action ↓ Mutation ↓ API ↓ Cache update / invalidation

Prefer predictable one-directional data flow. Components should not independently duplicate the same server state unless there is a clear reason.

7. Caching Strategy

For server data, decide:

  • How long data can be considered fresh.
  • When it should refetch.
  • How it is invalidated after mutations.
  • Whether stale data is acceptable.
  • How pagination/infinite queries are cached.
Request ↓ Cache hit? ── Yes → Return cached data │ No ↓ Fetch API ↓ Store cache ↓ Render

8. Loading, Error and Empty States

Request ├── Loading → Skeleton / Spinner ├── Success + data → Content ├── Success + no data → Empty state └── Error → Error UI + recovery

A production feature should design all four states, not just the success state.

9. Optimistic Updates

With an optimistic update, the UI changes immediately and the server operation completes in the background.

User clicks Like ↓ UI immediately shows Like ✓ ↓ Send API request ↙ ↘ Success Failure ↓ ↓ Keep UI Roll back + show error

Use it when the action is likely to succeed and the UI can safely recover if it fails.

10. Offline Support

Offline support means the application remains useful when the network is unavailable or unreliable.

User action ↓ Network available? ├── Yes → API └── No ↓ Local queue/cache ↓ Network returns ↓ Sync

For complex offline apps, conflict resolution becomes a major design decision.

12. Design a Data Table

Requirements might include sorting, filtering, pagination, selection, column resizing, virtualization, export and server-side queries.

DataTable ├── Toolbar │ ├── Search │ ├── Filters │ └── Export ├── Header │ ├── Sort │ └── Resize ├── Virtualized Body │ └── Row → Cell └── Pagination

Key design: For large datasets, prefer server-side filtering/sorting/pagination and row virtualization instead of rendering every row.

const query = {
  page,
  pageSize,
  sort,
  filters
};

useQuery({
  queryKey: ["users", query],
  queryFn: () => fetchUsers(query)
});

Data Table — Important Decisions

  • Client-side vs server-side operations.
  • Virtualization for large row counts.
  • Stable row IDs.
  • Column configuration model.
  • URL persistence for shareable filters.
  • Debounced search.
  • Cache per query.
  • Export on client or server depending on data size.

13. Design a File Explorer

FileExplorer ├── Toolbar ├── Breadcrumbs ├── Tree │ └── Folder │ ├── Folder │ └── File ├── File Grid/List └── Context Menu

Use a normalized model for large trees and lazy-load children when folders open.

{
  id: "folder-1",
  parentId: null,
  name: "Documents",
  type: "folder",
  childrenLoaded: false
}

File Explorer — Key Decisions

  • Tree state: expanded nodes, selected node.
  • Lazy-load folder children.
  • Virtualize very large directories.
  • Handle rename/move/delete optimistically only when rollback is safe.
  • Use stable IDs rather than array indexes.
  • Cache previously loaded folders.

14. Design a Dashboard

Dashboard ├── Header ├── Filters ├── KPI Cards ├── Charts ├── Tables └── Activity ↓ Multiple API queries ↓ Shared cache

Independent widgets should load independently where possible so one slow API does not block the entire dashboard.

Use skeletons per widget, cache server state and lazy-load heavy charting features if they are not needed immediately.

15. Design a Chat Application

Chat App ├── Conversation List ├── Message List ├── Composer └── User Presence │ ├── REST/HTTP → history └── WebSocket → live events

Use HTTP/API for initial history and mutations where appropriate, and WebSocket/SSE for real-time events.

Chat — Key Decisions

  • Paginate or cursor-load old messages.
  • Virtualize long message lists.
  • Keep scroll position stable.
  • Handle reconnects.
  • Deduplicate incoming messages.
  • Show optimistic messages with pending state.
  • Handle delivery/read states.
  • Cache conversations.

16. Design an Infinite Scroll Feed

Viewport ↓ Intersection Observer ↓ Near end? ↓ Fetch next cursor ↓ Append page ↓ Cache pages ↓ Repeat 
useInfiniteQuery({
  queryKey: ["feed"],
  queryFn: fetchFeed,
  getNextPageParam:
    page => page.nextCursor
});

Cursor pagination is often preferable to page numbers for changing feeds.

17. Design a Kanban Board

Board ├── Column │ ├── Card │ ├── Card │ └── Card ├── Column └── Column Drag ↓ Optimistic reorder ↓ Persist move ↓ Success / rollback

For drag-and-drop, keep transient drag state local, while board/task data belongs to shared/server state.

18. Design a Workflow Builder

Workflow Builder ├── Toolbar ├── Canvas │ ├── Node │ └── Edge ├── Properties Panel ├── Minimap └── Validation │ ↓ Workflow Model │ ↓ Save / Load API

Separate the visual editor state from the persisted workflow model. This makes undo/redo, validation and serialization easier.

Workflow Builder — Key Decisions

  • Normalized node/edge state.
  • Undo/redo history.
  • Selection and viewport state.
  • Autosave strategy.
  • Validation rules.
  • Conflict handling for collaborative editing.
  • Plugin/custom node architecture.
  • Viewport and rendering performance.

19. Design a Form Builder

Form Builder ├── Field Palette ├── Canvas │ └── Field ├── Properties Panel ├── Preview └── Schema ↓ JSON definition ↓ Renderer

Use a schema-driven model so the same schema can power rendering, validation and persistence.

{
  type: "text",
  name: "email",
  label: "Email",
  required: true
}

20. Design a Rich Text Editor

Separate editor state from persisted document state.

Editor ├── Toolbar ├── Document Model ├── Selection ├── History └── Plugins ↓ Serialize ↓ API / Storage

Use a structured document model rather than treating the editor as one giant HTML string when advanced editing features are required.

21. Design a Notification System

Event ↓ Notification service ↓ Client transport ├── WebSocket/SSE └── Polling fallback ↓ Notification store/cache ↓ UI ├── Toast └── Notification Center

Separate ephemeral toast notifications from persistent notification history.

22. Design a Theme System

Theme Provider ↓ Theme tokens ├── colors ├── spacing ├── typography └── shadows ↓ Components 
const theme = {
  colors: {
    primary: "...",
    background: "...",
    text: "..."
  }
};

Use design tokens so changing the theme does not require rewriting individual components.

23. Design a Search Component

Input ↓ Debounce ↓ Query ↓ Cache ↓ Results ├── Loading ├── Empty └── Error

Debounce user typing to avoid sending a request on every keystroke. Cancel or ignore stale requests when necessary.

24. Design a Multi-step Form

Step 1 ↓ Step 2 ↓ Step 3 ↓ Review ↓ Submit
  • Keep the overall draft in one form/state model.
  • Validate per step.
  • Preserve data when navigating backward.
  • Persist drafts if the form is long or important.
  • Handle server-side validation on final submission.

25. Design a Large Enterprise Application

App Shell ├── Auth ├── Router ├── Design System ├── Feature Modules │ ├── Users │ ├── Projects │ ├── Reports │ └── Settings ├── Shared API/Data Layer ├── Permissions └── Observability

Use feature-based architecture, clear boundaries, shared design primitives and consistent data-fetching/error patterns.

26. Feature-Based Architecture

src/
├── app/
│   ├── router/
│   └── providers/
├── features/
│   ├── users/
│   ├── projects/
│   └── reports/
├── components/
├── services/
├── hooks/
└── shared/

Keep feature-specific logic inside the feature and shared primitives in shared areas. Avoid a giant global "utils" folder containing unrelated business logic.

27. Extensibility

A scalable frontend should allow new features without rewriting the core.

Core ↓ Extension points ├── Plugins ├── Config ├── Renderers ├── Hooks └── Events ↓ New feature

Examples: custom table cell renderers, workflow node types, form field types and dashboard widgets.

28. Error Handling Architecture

API / Component Error ↓ Classify ├── Validation ├── Auth ├── Network └── Server ↓ Feature-level handling ↓ Fallback / Retry ↓ Global Error Boundary ↓ Logging / Monitoring

31. Trade-off Thinking

Senior-level interviews are less about finding one "perfect" architecture and more about explaining why you chose it.

QuestionExample reasoning
Client or server pagination?Server pagination for very large datasets; client pagination for small datasets already loaded.
Redux or local state?Local for isolated UI; shared store only when many distant consumers need synchronized client state.
Optimistic update?Use when failure can be rolled back cleanly and success is highly likely.
WebSocket or polling?WebSocket for frequent real-time updates; polling when simplicity and lower real-time requirements matter.
Cache aggressively?Yes when stale data is acceptable; otherwise use shorter freshness and precise invalidation.

Most Asked Interview Questions

  1. How do you approach frontend system design? Clarify requirements, define scale, design architecture, place state, define data flow, then cover performance, reliability, security, testing and trade-offs.
  2. How do you decide where state should live? Keep it as close as practical to its consumers; lift it only when multiple components need the same state.
  3. When would you use global state? For genuinely shared client state such as session information, app preferences or cross-feature workflows—not every piece of UI state.
  4. What is server state? Data owned by a backend that the frontend fetches, caches, synchronizes and mutates.
  5. Why use a server-state library? It can standardize caching, invalidation, retries, mutations, pagination and synchronization.
  6. How would you design a large data table? Server-side querying, stable row IDs, virtualization, debounced filters, caching and configurable columns.
  7. How would you handle a million-row dataset? Do not render/load it all in the browser; use server-side filtering/pagination/cursors and virtualize the visible rows.
  8. How would you design an infinite feed? Cursor-based pagination, cached pages, Intersection Observer, deduplication and virtualization if the list becomes large.
  9. How would you design a chat app? Fetch history through an API, receive live events through WebSocket/SSE, cache conversations, reconcile messages and handle reconnects.
  10. How would you design a workflow builder? Separate editor state from persisted workflow state, normalize nodes/edges, support undo/redo, validation and extensible node types.
  11. How would you design a form builder? Use a schema-driven model that defines fields, validation and rendering, then build a renderer and editor around that schema.
  12. How would you design a notification system? Separate persistent notification history from ephemeral toasts and use a real-time transport where needed.
  13. How would you design a theme system? Define design tokens and expose them through a provider/theme mechanism so components consume semantic tokens rather than hardcoded values.
  14. What is optimistic UI? Updating the UI before server confirmation, then confirming or rolling back based on the result.
  15. How do you handle offline support? Cache useful data locally, queue supported mutations, synchronize when connectivity returns and design conflict resolution.
  16. How do you make a frontend scalable? Use clear feature boundaries, state ownership, caching, code splitting, virtualization, reusable primitives and consistent conventions.
  17. What is a trade-off in frontend architecture? A decision where improving one property usually adds cost or complexity elsewhere, such as caching vs freshness.
  18. How do you prevent one failed API from breaking a dashboard? Isolate widgets, give each query its own loading/error state and use boundaries/fallbacks where appropriate.
  19. How would you design an enterprise React application? Feature-based architecture, app shell, routing, design system, shared data layer, permissions, observability, testing and strict module boundaries.
  20. How do you avoid overengineering? Start with actual requirements and scale, choose the simplest architecture that meets them, and add complexity only when a measured need appears.

Scenario-Based Questions

  1. A table has 500,000 rows.
    Use server-side filtering/sorting and cursor or page-based fetching. Render only visible rows with virtualization.
  2. Five distant components need the selected project.
    Move that state to an appropriate shared owner/store rather than passing it through many unrelated components.
  3. A modal is used by only one page.
    Keep its open/close state local to that feature; global state would add unnecessary coupling.
  4. A dashboard has 12 independent API calls.
    Use a server-state/cache layer, allow independent loading, cache results and avoid blocking the entire dashboard on one slow widget.
  5. A search box sends 20 requests while typing.
    Debounce input, cancel/ignore stale requests and cache recent queries where useful.
  6. A chat message appears twice after reconnecting.
    Give messages stable IDs and deduplicate incoming events before updating the message list.
  7. A chat app loses connection.
    Show connection status, reconnect with bounded backoff, resynchronize missed events and reconcile local state.
  8. A Kanban drag succeeds visually but the server rejects it.
    Rollback the optimistic change and explain the failure to the user.
  9. A workflow builder becomes slow with 2,000 nodes.
    Profile rendering, reduce unnecessary updates, virtualize/optimize where possible and keep node state normalized/selective.
  10. A form builder needs 50 field types.
    Use a field registry/schema-driven architecture so new field types can be added without modifying a giant conditional renderer.
  11. An enterprise app has 20 teams creating UI components.
    Introduce a design system, ownership rules, documentation and reusable primitives with clear feature boundaries.
  12. Users must share a filtered table URL.
    Store shareable filter/sort/page state in URL search parameters and keep server data in the cache layer.
  13. A feed changes while the user scrolls.
    Use cursor pagination and stable IDs; reconcile new items carefully so the user's scroll position is not unexpectedly disrupted.
  14. A user edits a document offline.
    Persist a local draft/operation queue and synchronize later. For multi-user editing, define a conflict-resolution strategy rather than blindly overwriting server state.
  15. A dashboard chart library is huge.
    Lazy-load the chart feature or split charting libraries from the initial bundle if the charts are not immediately required.

  • ✔ Use caching for server data when useful.
  • ✔ Design loading + success + empty + error states.
