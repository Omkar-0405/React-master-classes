Simple Interview Handbook • Cookies • Local Storage • Session Storage • IndexedDB

What is Browser Storage?

Browser storage lets a web application keep data on the user's device so it can be used again later.

Web App │ ├── Cookies ├── localStorage ├── sessionStorage └── IndexedDB

They differ mainly in size, lifetime, access, and purpose.

1. Cookies

Cookies are small pieces of data associated with a website. They are commonly used for sessions, authentication-related state, preferences and tracking.

document.cookie = "theme=dark; Max-Age=3600; Path=/";

A cookie can be sent to the server automatically with matching HTTP requests.

Important Security Flags

  • HttpOnly: JavaScript cannot read the cookie.
  • Secure: sent only over HTTPS.
  • SameSite: controls cross-site sending behavior.

Security: Sensitive authentication cookies are commonly protected with HttpOnly, Secure and an appropriate SameSite policy.

2. Local Storage

localStorage stores string key-value data that normally remains after the browser tab and browser are closed.

localStorage.setItem("theme", "dark");

const theme = localStorage.getItem("theme");

localStorage.removeItem("theme");
// localStorage.clear();

Objects must be serialized:

localStorage.setItem("user", JSON.stringify(user));

const user = JSON.parse(
  localStorage.getItem("user")
);

It is synchronous and should not be used for large or performance-sensitive data.

3. Session Storage

sessionStorage also stores string key-value data, but its lifetime is tied to the page session/tab.

sessionStorage.setItem("step", "2");

const step = sessionStorage.getItem("step");

It is useful for temporary UI state such as a multi-step form or temporary navigation data.

4. IndexedDB

IndexedDB is a browser database for storing larger amounts of structured data, including objects and binary data.

Web App │ ▼ IndexedDB │ ├── Database ├── Object Stores └── Indexes
const request = indexedDB.open("AppDB", 1);

request.onupgradeneeded = event => {
  const db = event.target.result;
  db.createObjectStore("users", { keyPath: "id" });
};

It is asynchronous and suitable for offline-capable applications and larger client-side datasets.

Cookies vs localStorage

Cookie Browser ─────────► Server sent with request localStorage Browser ─────────X Server stays in browser

This difference is one of the most important interview points.

Security: Where should tokens go?

Do not blindly store sensitive authentication tokens in JavaScript-readable storage. If a session mechanism uses cookies, an HttpOnly + Secure + appropriate SameSite cookie can reduce exposure to token theft through JavaScript.

Storage choice depends on the application's threat model and architecture. There is no universal "best storage" for every authentication design.

React Connection

useEffect(() => {
  localStorage.setItem(
    "theme",
    theme
  );
}, [theme]);

Browser storage is external to React state. Read it at appropriate times and synchronize it deliberately rather than treating it as a replacement for React state.

Most Asked Interview Questions

  1. What is browser storage? A set of browser mechanisms for keeping application data on the client.
  2. Cookies vs localStorage? Cookies can be sent with HTTP requests; localStorage stays client-side.
  3. localStorage vs sessionStorage? localStorage is persistent; sessionStorage is tied to the page session.
  4. Can localStorage store objects directly? No. Values are strings, so use JSON serialization for JSON-compatible objects.
  5. What is IndexedDB? An asynchronous browser database for structured client-side data.
  6. Which storage is best for large structured offline data? IndexedDB.
  7. Can JavaScript read an HttpOnly cookie? No.
  8. Are cookies automatically sent to the server? Matching cookies can be sent with HTTP requests according to cookie rules.
  9. Is localStorage synchronous? Yes, its API is synchronous.
  10. Does sessionStorage survive closing the browser? It is associated with a page session and normally does not survive the end of that session.
  11. Can browser storage be used for sensitive data? Be cautious; XSS and other threats matter. Choose storage based on the security model.
  12. Why use IndexedDB instead of localStorage? For larger structured data and asynchronous database operations.

Scenario-Based Questions

  1. Remember a user's theme across visits.
    Use localStorage.
  2. Keep a multi-step form state only for the current tab/session.
    Use sessionStorage when simple string data is sufficient.
  3. The server needs a session identifier on requests.
    A cookie is a natural mechanism.
  4. Store thousands of structured offline records.
    Use IndexedDB.
  5. Store a JSON-compatible object in localStorage.
    Use JSON.stringify when writing and JSON.parse when reading.
  6. You need JavaScript to be unable to read an authentication cookie.
    Use an HttpOnly cookie, with Secure and appropriate SameSite settings.
  7. You want a value to survive browser restarts.
    Use persistent localStorage or an appropriately persistent cookie, depending on the requirement.
  8. You need a temporary value that should not remain after the page session ends.
    Consider sessionStorage.
  9. You want client-side data shared with the server automatically.
    Cookies can be sent with requests; localStorage and IndexedDB are not automatically sent.
  10. You need a browser cache-like database for an offline-first app.
    IndexedDB is a strong fit.
  11. You store a secret in localStorage because it is convenient.
    Reconsider the design; JavaScript-readable storage can be exposed by XSS.
  12. You need to store a small preference and read it synchronously.
    localStorage is often suitable.

Quick Revision

  • ✔ Cookies = small + can be sent to server.
  • ✔ localStorage = persistent string key-value storage.
  • ✔ sessionStorage = temporary page-session storage.
  • ✔ IndexedDB = larger structured browser database.
  • ✔ HttpOnly = JavaScript cannot read cookie.
  • ✔ Secure = HTTPS only.
  • ✔ SameSite = controls cross-site cookie behavior.
  • ✔ Do not treat client storage as automatically secure.
