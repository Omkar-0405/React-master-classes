1. Performance — Big Picture

React performance is mainly about doing less unnecessary work and keeping important interactions responsive.

Slow UI? ↓ Measure first ↓ Find bottleneck ↓ Choose the right optimization ↓ Measure again Common tools: Memoization • State Colocation • Code Splitting Lazy Loading • Virtualization • Better data flow
Interview rule: Do not say "useMemo/useCallback everywhere." First identify why the component is rendering or why the work is expensive.

2. React.memo

React.memo memoizes a function component. If its props are considered equal, React can skip re-rendering that component when its parent renders.

const User = React.memo(function User({ name }) {
  return <h2>{name}</h2>;
});

By default, React compares props using shallow/object identity comparison.

React.memo — Important Limitation

const Child = React.memo(({ onClick }) => {
  return <button onClick={onClick}>Click</button>;
});

function Parent() {
  const handleClick = () => {
    console.log("click");
  };

  return <Child onClick={handleClick} />;
}

handleClick is a new function on each parent render, so the child receives a new prop reference and memoization may not help.

Use useCallback when stable callback identity is actually useful.

3. useMemo

useMemo caches a calculated value until dependencies change.

const filtered = useMemo(() => {
  return products.filter(p =>
    p.name.includes(search)
  );
}, [products, search]);

Best suited for genuinely expensive calculations or for preserving a value's identity when another optimization depends on it.

useMemo — Overuse

Memoization itself has a cost: dependency tracking, memory and extra complexity.

// Often unnecessary
const fullName = useMemo(
  () => firstName + " " + lastName,
  [firstName, lastName]
);

For cheap calculations, normal JavaScript is often better.

4. useCallback

useCallback caches a function reference.

const handleSelect = useCallback((id) => {
  setSelected(id);
}, []);

It is useful mainly when:

  • Passing a callback to a memoized child.
  • A stable function reference matters to another Hook/API.

React.memo + useCallback

const Button = React.memo(function Button({ onClick }) {
  console.log("Button render");
  return <button onClick={onClick}>Save</button>;
});

function Parent() {
  const save = useCallback(() => {
    console.log("save");
  }, []);

  return <Button onClick={save} />;
}
Parent render ↓ useCallback → same function reference ↓ React.memo → props unchanged ↓ Child can skip render

5. Code Splitting

Code splitting breaks a large JavaScript bundle into smaller chunks that can be loaded when needed.

One large bundle ↓ Split into chunks / | \ Home Dashboard Admin ↓ ↓ ↓ load when needed

This can reduce the JavaScript needed for the initial page.

React.lazy

React.lazy lets a component be loaded dynamically.

const Admin = React.lazy(
  () => import("./Admin")
);

The imported module is loaded when React needs to render that lazy component.

Suspense

Suspense provides fallback UI while a lazy component or another supported Suspense-enabled operation is waiting.

<Suspense fallback={<p>Loading...</p>}>
  <Admin />
</Suspense>
Easy memory: React.lazy = load component later. Suspense = show fallback while waiting.

6. Bundle Optimization

The goal is to reduce the amount of JavaScript the browser needs to download, parse and execute.

  • Code split routes/features.
  • Remove unused dependencies.
  • Prefer tree-shakeable packages.
  • Avoid importing huge libraries for tiny features.
  • Analyze production bundles.
  • Compress and cache assets.
// Prefer a focused import when supported
import debounce from "some-library/debounce";

Exact tree-shaking behavior depends on the library and build tool.

7. Lazy Loading

Lazy loading means delaying the loading of something until it is needed.

ExampleWhy?
Admin routeMost users may never open it.
Large chartLoad only when chart is visible/needed.
Heavy editorAvoid loading it on every page.

Lazy loading is useful when it improves the critical initial path. Too many tiny chunks can also add overhead.

8. Virtualization

Virtualization renders only the visible portion of a large list instead of creating thousands of DOM nodes at once.

10,000 rows ┌────────────────────┐ │ Row 120 ← visible │ │ Row 121 │ │ Row 122 │ │ Row 123 │ └────────────────────┘ Only visible/nearby rows are mounted. As user scrolls: old rows removed → new rows rendered

This can greatly reduce DOM work and memory for very large lists.

react-window / react-virtualized

These libraries provide virtualization techniques for large lists and grids.

LibraryUse
react-windowLightweight virtualization for lists/grids.
react-virtualizedOlder, feature-rich virtualization library.

Choose based on your project's requirements and current library support.

9. Prevent Unnecessary Re-renders

First understand what is causing the render.

  • Keep state close to where it is used.
  • Split large components.
  • Use React.memo when a component benefits from memoization.
  • Stabilize expensive callback/value props when needed.
  • Avoid creating unnecessary derived state.
  • Use virtualization for huge collections.
  • Use transitions/deferred values for suitable non-urgent work.
A re-render is not automatically a performance problem. React can re-render and still make no DOM changes.

10. State Colocation

State colocation means keeping state as close as possible to the components that actually use it.

❌ State too high App ↓ Huge state object ↓ Many unrelated children ✔ State colocated App ├── Header └── SearchBox └── search state

When search state lives inside SearchBox, unrelated parts of the app do not need to participate in that state flow.

Why State Colocation Helps

function SearchBox() {
  const [query, setQuery] = useState("");

  return (
    <input
      value={query}
      onChange={e => setQuery(e.target.value)}
    />
  );
}

Keeping temporary UI state local can reduce the number of components affected by updates and makes ownership clearer.

12. Performance Profiling — React DevTools

The React DevTools Profiler helps identify which components render, how often they render, and where rendering time is spent.

Profiler ↓ Record interaction ↓ Inspect commits ↓ Find expensive components ↓ Check why they render ↓ Optimize ↓ Profile again

Use profiling to validate that an optimization actually improves the real application.

What to Look For in the Profiler

  • Components rendering more often than expected.
  • Expensive render durations.
  • Large commits.
  • Parent updates causing unrelated child work.
  • Expensive calculations.
  • Interactions that feel slow.

Performance Optimization Order

1. Measure ↓ 2. Fix unnecessary work ↓ 3. Colocate state ↓ 4. Split large components ↓ 5. Virtualize huge lists ↓ 6. Code split large features ↓ 7. Memoize targeted bottlenecks ↓ 8. Measure again

Most Asked Interview Questions

  1. What is React.memo? A memoization mechanism that can skip a function component's render when its props are equal.
  2. When should you use React.memo? When a component re-renders often with the same props and skipping its render is beneficial.
  3. What is useMemo? It caches a calculated value between renders.
  4. What is useCallback? It caches a function reference between renders.
  5. useMemo vs useCallback? useMemo caches a value; useCallback caches a function.
  6. Why can useMemo/useCallback hurt performance? They add dependency/memoization overhead and complexity.
  7. What is code splitting? Splitting JavaScript into chunks loaded when needed.
  8. React.lazy vs Suspense? lazy defines a dynamically loaded component; Suspense provides fallback UI while it is waiting.
  9. What is virtualization? Rendering only visible items from a large collection.
  10. Why use virtualization? To reduce DOM nodes, rendering work and memory for very large lists.
  11. What is state colocation? Keeping state close to the components that use it.
  12. How do you prevent unnecessary re-renders? Fix state/data flow first, then use targeted memoization, stable props, colocation and virtualization where appropriate.
  13. How do you profile React performance? Use React DevTools Profiler to inspect renders and commits, then measure after changes.
  14. Does every re-render mean the DOM changes? No. React can render/reconcile and determine that no DOM update is necessary.
  15. How do you optimize a large initial bundle? Analyze the bundle, remove unnecessary dependencies, code split large features and lazy load non-critical code.

Scenario-Based Questions

  1. A memoized child still renders every time the parent renders.
    Check whether its props contain new object/function references. Stabilize them only if the optimization is useful.
  2. A child receives a callback created inside the parent.
    If the child is memoized and callback identity is causing renders, consider useCallback.
  3. A calculation filters 100,000 records on every render.
    Profile it; if genuinely expensive, consider useMemo or moving the work elsewhere.
  4. A simple string concatenation is wrapped in useMemo.
    Remove it unless there is a specific identity/performance reason; the calculation is cheap.
  5. The application downloads a huge admin module even for normal users.
    Use route/feature code splitting and lazy loading.
  6. A page contains 20,000 table rows.
    Use virtualization rather than rendering every row into the DOM.
  7. A search input causes the entire application to re-render.
    Consider colocating the search state and inspect the component tree.
  8. A global state update causes many unrelated components to update.
    Review state ownership, context boundaries and subscriptions; colocate state where possible.
  9. A developer adds React.memo to every component.
    Do not blindly memoize. Measure first and target components with actual rendering costs.
  10. A large list scrolls poorly.
    Profile it and consider virtualization, reducing expensive row rendering, and avoiding unnecessary layout work.
  11. A component is expensive only because it receives a constantly recreated object prop.
    Check whether the object can be derived/stabilized appropriately and whether React.memo then provides value.
  12. A route is rarely visited.
    Lazy load/code split that route so it does not have to be part of the initial JavaScript.
  13. The React Profiler shows an unexpected large commit.
    Inspect which components rendered and why, then optimize the actual bottleneck.
  14. After adding useMemo, the app becomes more complex but no faster.
    Remove the unnecessary memoization and prefer simpler code.
  15. A user types into a large searchable UI and typing feels delayed.
    Consider state colocation and, where appropriate, useTransition/useDeferredValue plus efficient rendering/virtualization.
