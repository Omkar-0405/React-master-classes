Section 6 — React Rendering Internals

Simple Interview Handbook • Fiber • Reconciliation • Virtual DOM • Concurrent Rendering • Batching • Strict Mode

1. Big Picture

React rendering can be understood as two major jobs: render and commit.

State / Props / Context change ↓ RENDER PHASE Calculate next UI tree ↓ Reconciliation ↓ COMMIT PHASE Apply necessary DOM changes ↓ Browser ↓ Screen
Important: Rendering is mainly calculation. The commit phase is where React applies the required changes to the host environment, such as the browser DOM.

2. Fiber Architecture

Fiber is React's internal architecture for representing work on the component tree and managing that work over time.

A Fiber node stores information React needs about a component/element, including its type, relationships in the tree, pending work and other bookkeeping.

Fiber tree App / \ Header Main / \ List Sidebar Each node is represented internally by a Fiber.

Fiber made it possible for React to organize rendering work into smaller units and support interruptible/concurrent rendering behavior.

Fiber Node — Simple View

You do not need to memorize every internal field for most interviews. Know the concept.

3. Scheduler

React needs to decide when rendering work should be performed. Its scheduling system helps React prioritize and coordinate work instead of treating every update as equally urgent.

Updates arrive ↓ React assigns priority ↓ Work is scheduled ↓ Higher-priority work can be handled first ↓ Render ↓ Commit

Think of the scheduler as a traffic controller for rendering work, not as the code that directly updates the DOM.

4. Incremental Rendering

Fiber lets React break rendering work into smaller units rather than treating a large render as one indivisible operation.

Large render ↓ [Work 1] → [Work 2] → [Work 3] → [Work 4] ↑ React can manage work between units

This architecture is important for React's concurrent rendering capabilities.

5. Reconciliation

Reconciliation is React's process of comparing the previous React element tree with the next one and determining what needs to change.

Previous tree Next tree │ │ └────── Compare ──────┘ ↓ Determine changes ↓ Commit required work

6. Tree Diffing

React uses heuristics to compare trees efficiently rather than performing a general-purpose minimum-edit-tree algorithm.

  • If element types differ, React generally replaces the old subtree.
  • If the same element type remains, React updates relevant props/attributes and continues comparing children.
  • Keys help React match items in collections.

7. Why O(n)?

A naive comparison of arbitrary trees can be very expensive. React uses practical assumptions and heuristics to make reconciliation approximately O(n) for common tree comparisons.

General tree diff Potentially expensive React assumptions ↓ Different types → replace subtree Same type → compare/update Keys → match list children ↓ Practical near-linear reconciliation

Interview answer: React achieves practical O(n)-style reconciliation by making assumptions about element types and using keys to identify children.

8. Element Matching

React needs to know which old element corresponds to which new element.

// Stable identity
items.map(item => (
  <Row key={item.id} item={item} />
));

A stable key tells React that an item is the same logical item across renders even when its position changes.

9. Virtual DOM

The Virtual DOM is a simplified way to describe React's in-memory representation of UI elements. React creates element descriptions during rendering, compares the new result with the previous one, and commits necessary host changes.

JSX ↓ React elements ↓ Fiber / internal tree ↓ Reconciliation ↓ Commit ↓ Real DOM

Important: Virtual DOM is not a magical faster DOM. Its value is that React can calculate UI changes declaratively and coordinate rendering work.

10. Creation → Diff → Commit

function App({ count }) {
  return <h1>Count: {count}</h1>;
}
1. Creation JSX → React element description 2. Diff / Reconciliation Previous result ↔ Next result 3. Commit Apply required host changes 4. Browser Paints updated pixels

11. Concurrent Rendering

Concurrent rendering means React can work on rendering without necessarily blocking the browser for the entire calculation. Rendering work can be paused, resumed, restarted or abandoned before it commits.

Important: Concurrent rendering does not mean React renders everything simultaneously on multiple threads.

12. Interruptible Rendering

Start rendering low-priority work ↓ Work for a while ↓ Urgent update arrives ↓ Pause / switch work ↓ Handle urgent update ↓ Continue or restart previous work

This helps React keep urgent interactions responsive when expensive UI work is happening.

13. Priority Scheduling

Not every update has the same urgency.

ExampleTypical idea
Typing / direct interactionShould remain responsive.
Showing a large filtered resultMay be treated as less urgent.
Transition between screens/tabsCan often be marked as a transition.

startTransition is one API developers use to mark updates as non-urgent.

14. Automatic Batching — React 18

React 18 expanded automatic batching so updates from more asynchronous contexts can be batched when using the modern React root API.

setTimeout(() => {
  setCount(c => c + 1);
  setName("Omkar");
}, 1000);

React can process these updates together rather than necessarily causing a separate render for each setter.

Interview point: Batching reduces rendering work. It does not mean state variables immediately change after calling a setter.

15. Before vs React 18 Batching

SituationOlder React behaviorReact 18+
React event handlerBatching existedBatching exists
Timeout / promise callbackOften not automatically batchedAutomatically batched in modern roots

React 18 introduced broader automatic batching as part of its concurrent rendering architecture.

16. Strict Mode

<StrictMode> is a development-time tool that helps identify unsafe patterns and accidental side effects.

import { StrictMode } from "react";

createRoot(document.getElementById("root")).render(
  <StrictMode>
    <App />
  </StrictMode>
);

Strict Mode does not affect production behavior in the same way. Some development-only checks intentionally invoke rendering/effect setup patterns more than once.

17. Why Does Strict Mode "Double Render"?

In development, React may call component rendering logic more than once to expose accidental side effects inside render.

Development Strict Mode Render ↓ Render again ↓ Check for unsafe side effects ↓ Normal development flow

For Effects, React can also perform an extra setup → cleanup → setup cycle in development. This helps reveal missing cleanup.

Why? To make impure rendering and unsafe Effects easier to detect before production.

18. Strict Mode Example

function App() {
  console.log("render");

  useEffect(() => {
    console.log("effect");

    return () => {
      console.log("cleanup");
    };
  }, []);

  return <h1>Hello</h1>;
}

With development Strict Mode, you may see extra render/effect lifecycle activity. Do not "fix" this by adding random flags; make rendering pure and Effect cleanup correct.

Most Asked Interview Questions

  1. What is Fiber? React's internal architecture that represents rendering work as units and enables scheduling and concurrent rendering capabilities.
  2. What is a Fiber node? An internal node containing information React needs to process a component/element and its relationships/work.
  3. Why was Fiber introduced? To make rendering work more flexible, schedulable and interruptible.
  4. What is reconciliation? Comparing previous and next React trees to determine necessary changes.
  5. Why is React reconciliation approximately O(n)? React uses heuristics such as element type comparison and keys rather than arbitrary expensive tree matching.
  6. Why are keys important? They provide stable identity so React can match children correctly.
  7. What is the Virtual DOM? An in-memory representation/description of UI that React uses during rendering and reconciliation.
  8. What are render and commit phases? Render calculates the next UI; commit applies the required host changes.
  9. What is concurrent rendering? A rendering model where React can schedule and interrupt rendering work before committing it.
  10. Can concurrent rendering run on multiple threads? No. It does not mean React is automatically rendering components on multiple CPU threads.
  11. What is incremental rendering? Breaking rendering work into manageable units that React can schedule rather than treating all work as one indivisible operation.
  12. What is automatic batching? React groups multiple state updates into fewer rendering passes when batching applies.
  13. What changed with automatic batching in React 18? Batching was expanded to more asynchronous contexts when using the modern root API.
  14. Why does Strict Mode render components twice? In development, extra checks help reveal impure rendering and unsafe side effects.
  15. Does Strict Mode double render in production? The development-only checks are not performed the same way in production.
  16. Why does Strict Mode run Effect setup/cleanup more than once in development? To expose Effects that are missing or incorrectly handling cleanup.

Scenario-Based Questions

  1. A component has an expensive render and the user starts typing.
    Concurrent rendering and priority mechanisms can help React keep urgent interaction responsive; consider transitions for non-urgent work.
  2. A low-priority UI update is running when an urgent update arrives.
    React can interrupt/reprioritize rendering work before committing the lower-priority result.
  3. A developer thinks Fiber means every component runs in a separate thread.
    Incorrect. Fiber is an internal work architecture; concurrent rendering does not automatically mean multithreaded rendering.
  4. A list is reordered and component state appears attached to the wrong item.
    Check the list keys. Use stable item identity rather than indexes.
  5. A completely different element type replaces another element.
    React generally treats the subtree as a replacement rather than trying to update it as the same type.
  6. Two state setters inside a timeout cause multiple renders in React 18.
    With the modern React root, React 18 can automatically batch them.
  7. A state variable does not show its new value immediately after setState.
    State updates schedule a future render; the current render's state value does not mutate immediately.
  8. A developer performs an API call directly inside component render.
    Move the side effect out of render. Render should be pure, especially because concurrent rendering can restart rendering.
  9. An Effect runs twice in development.
    Check Strict Mode. Development Strict Mode intentionally performs extra setup/cleanup checks.
  10. An Effect opens a WebSocket but never closes it.
    Add cleanup. Strict Mode may expose this problem during development.
  11. A developer removes StrictMode because of duplicate logs.
    Do not use removal as the fix. Make render pure and Effect cleanup correct; the extra development checks are intentional.
  12. A parent re-renders but the DOM does not visibly change.
    React can re-render/calculates a new tree and then reconcile it without making unnecessary DOM changes.
  13. A developer says Virtual DOM is always faster than direct DOM.
    That is too broad. Virtual DOM is an abstraction that lets React declaratively calculate and coordinate updates; performance depends on the workload.
  14. A large UI update blocks interaction.
    Consider whether the update can be marked as non-urgent with startTransition and whether expensive rendering can be optimized.
  15. You need to explain Fiber in one sentence.
    Fiber is React's internal architecture for breaking rendering work into units that can be scheduled and managed over time.
