1. What is Project Architecture?

Project architecture is how we organize code, responsibilities and dependencies so an application remains understandable and maintainable as it grows.

Small App ↓ Few files ↓ Simple structure Large App ↓ Many features + teams ↓ Need boundaries ↓ Clear architecture
Interview idea: There is no single perfect folder structure. The goal is clear ownership, low coupling, high cohesion and easy change.

2. A Simple Folder Structure

src/
├── components/
├── pages/
├── hooks/
├── services/
├── utils/
├── types/
├── assets/
├── styles/
├── routes/
└── App.tsx

This is a simple layer-oriented structure. It can work well for small applications.

Layer-Based Structure

UI ↓ Pages / Components ↓ Hooks ↓ Services / API ↓ Backend Shared: utils / types / constants / styles

Problem at scale: files for one feature can become scattered across many folders.

3. Feature-Based Architecture

Feature-based architecture groups code by business feature rather than technical type.

src/
├── features/
│   ├── auth/
│   │   ├── components/
│   │   ├── hooks/
│   │   ├── services/
│   │   ├── types.ts
│   │   └── index.ts
│   │
│   ├── users/
│   │   ├── components/
│   │   ├── hooks/
│   │   ├── services/
│   │   └── types.ts
│   │
│   └── orders/
│       ├── components/
│       ├── hooks/
│       ├── services/
│       └── types.ts
│
├── shared/
└── app/

Everything needed for a feature is closer together.

Feature-Based Flow

User Feature ├─ UI ├─ hooks ├─ API ├─ types └─ tests ↓ Self-contained feature ↓ Other features depend only on explicit public APIs

4. Feature-Based vs Layer-Based

Layer-BasedFeature-Based
Groups by technical role.Groups by business capability.
Easy for small apps.Scales well for larger apps.
Feature code can be scattered.Feature code stays together.
Simple initial setup.Needs clearer boundaries.

5. Atomic Design

Atomic Design organizes UI into increasing levels of complexity.

Atoms ↓ Buttons, inputs, icons ↓ Molecules ↓ Search box, form field ↓ Organisms ↓ Header, data table ↓ Templates ↓ Page layout ↓ Pages ↓ Actual screen

It is primarily a UI composition methodology, not a complete application architecture.

Atomic Design Example

components/
├── atoms/
│   ├── Button.tsx
│   └── Input.tsx
├── molecules/
│   ├── SearchBox.tsx
│   └── FormField.tsx
├── organisms/
│   ├── Header.tsx
│   └── UserTable.tsx
├── templates/
└── pages/
Do not force every component into an atomic category. If the classification adds confusion, a simpler component structure may be better.

6. Modular Design

Modular design divides the application into modules with clear responsibilities and boundaries.

Application ├── Auth Module ├── User Module ├── Order Module └── Reporting Module Each module: - owns related code - exposes a small public API - hides internal details

The goal is to reduce coupling and make changes safer.

Module Boundary Example

// features/users/index.ts
export {
  UserList,
  useUsers
} from "./public";

export type {
  User
} from "./types";

Consumers should ideally depend on the module's public API rather than its internal files.

7. Separation of Concerns

Separation of Concerns (SoC) means keeping different responsibilities separate.

Component → rendering / UI Hook → UI-related state / behavior Service → API communication Utility → reusable pure logic Store → shared application state Types → contracts

Bad Separation

function UserPage() {
  // UI
  // API calls
  // validation
  // transformation
  // global state
  // business rules
  // local state
  // formatting
  // 500 lines later...
}

Large components become difficult to test and change.

Better Separation

// UserPage.tsx
const { users, loading } = useUsers();

return <UserTable users={users} loading={loading} />;

// useUsers.ts
// state + UI-facing behavior

// userService.ts
// API calls

// userUtils.ts
// pure transformations

8. Shared Components

A shared component is reusable across multiple features.

shared/
├── components/
│   ├── Button/
│   ├── Modal/
│   ├── Input/
│   └── DataTable/
├── hooks/
├── utils/
└── types/

Good shared components solve repeated problems without knowing feature-specific business rules.

When Should a Component Become Shared?

  • Used by multiple features.
  • Has a stable API.
  • Represents a common UI pattern.
  • Its behavior is not tied to one business domain.
Don't abstract too early: Two similar components are not automatically the same abstraction. Wait until the shared behavior is clear.

9. Barrel Exports

A barrel file re-exports multiple modules from a single entry point.

// components/index.ts
export { Button } from "./Button";
export { Modal } from "./Modal";
export { Input } from "./Input";

Then:

import {
  Button,
  Modal,
  Input
} from "@/components";

Barrel Export — Advantages

  • Cleaner imports.
  • Defines a public API.
  • Hides internal file structure.
  • Can improve discoverability.

Tradeoff: Large or poorly designed barrels can complicate dependency graphs and, depending on tooling, affect tree-shaking or module loading behavior.

10. Design Systems

A design system is a shared collection of UI components, design tokens, rules and usage guidance.

Design System ├── Tokens │ ├── Colors │ ├── Spacing │ ├── Typography │ └── Radius │ ├── Components │ ├── Button │ ├── Input │ ├── Modal │ └── Table │ └── Guidelines ├── Accessibility ├── Usage └── Patterns

Design System vs Component Library

Component LibraryDesign System
Reusable UI components.Components + tokens + guidelines + patterns.
Focuses on implementation.Also defines design and product consistency.
Example: Button, Modal, Table.Also defines when/how those components should be used.

11. Architecture Dependency Direction

Clear dependency direction prevents circular dependencies and tight coupling.

App / Features ↓ Shared UI / Shared Utilities ↓ Low-level helpers Avoid: Shared → Feature A → Feature B → Shared ↑ cycles

Not every application needs a strict hierarchy, but dependencies should be intentional.

12. Avoid the "Shared" Dumping Ground

Putting everything reusable-looking into shared/ can create a huge dependency-heavy folder.

shared/
├── UserBusinessRules.ts ❌
├── OrderCalculation.ts ❌
├── AuthLogic.ts ❌
├── Button.tsx
└── DateFormat.ts

Business logic should normally remain near its owning feature/domain unless it is genuinely cross-domain.

13. Testing Architecture

Keep tests close to the code when that improves discoverability.

features/
└── users/
    ├── components/
    │   ├── UserList.tsx
    │   └── UserList.test.tsx
    ├── hooks/
    │   ├── useUsers.ts
    │   └── useUsers.test.ts
    └── services/
        ├── userService.ts
        └── userService.test.ts

Project-wide E2E tests can live separately because they represent application journeys rather than one module.

15. Architecture Principles

  • High cohesion: related code stays together.
  • Low coupling: modules know as little as practical about each other.
  • Clear boundaries: modules expose intentional APIs.
  • Single responsibility: avoid giant components/services.
  • Dependency direction: avoid accidental circular dependencies.
  • Reuse carefully: abstract repeated behavior only when the abstraction is clear.
  • Consistency: shared design tokens and patterns reduce UI drift.

16. Architecture Tradeoffs

Too SimpleToo Complex
Scattered responsibilities as app grows.Many folders/abstractions for a small app.
Harder ownership.Harder onboarding.
Duplication may grow.Simple changes require many files.
Best answer in interviews: Architecture should match the application's size, domain complexity and team structure. Do not introduce complexity without a problem to solve.

Most Asked Interview Questions

  1. What is project architecture? The organization of code, responsibilities, modules and dependencies in an application.
  2. What folder structure do you prefer? For small apps, a simple layer structure can work; for larger apps, feature-based architecture often keeps business code cohesive.
  3. What is feature-based architecture? Code is grouped around business features such as auth, users and orders.
  4. Why use feature-based architecture? It keeps related code together and can make large applications easier to maintain.
  5. What is Atomic Design? A UI methodology that organizes components into atoms, molecules, organisms, templates and pages.
  6. Is Atomic Design a complete architecture? No. It mainly describes UI composition and should not replace application/domain architecture.
  7. What is modular design? Splitting the system into modules with clear responsibilities and public boundaries.
  8. What is Separation of Concerns? Keeping different responsibilities separate so each part is easier to understand and change.
  9. What makes a good shared component? It solves a genuinely common problem and has a stable, feature-independent API.
  10. What is a barrel export? A file that re-exports modules through a single public entry point.
  11. Are barrel exports always good? No. They improve imports but poorly designed barrels can complicate dependencies or bundling.
  12. What is a design system? Shared design tokens, components, patterns and usage guidelines that create consistent UI.
  13. Design system vs component library? A component library focuses on reusable implementation; a design system also includes tokens, guidelines and patterns.
  14. What is high cohesion? Related responsibilities are grouped together.
  15. What is low coupling? Modules depend on as little implementation detail of other modules as practical.
  16. Should all reusable code go into shared? No. Business-specific code should remain close to its owning feature.
  17. How do you prevent circular dependencies? Define dependency direction, keep module boundaries clear and inspect the dependency graph when necessary.
  18. How do you choose an architecture? Consider application size, domain complexity, team size, change patterns and deployment requirements.

Scenario-Based Questions

  1. A 50-line app has 15 architecture folders.
    Simplify it. Architecture should solve real complexity, not create it.
  2. A large app has components, hooks and services scattered by type.
    Consider feature-based organization so each business capability owns its related code.
  3. The User feature needs a user-specific validation rule.
    Keep the rule inside the users feature rather than placing it in shared just because it is a utility.
  4. Three features use the same Button.
    Move the genuinely reusable Button into the shared/design-system layer.
  5. Two components look similar but have different business rules.
    Do not immediately merge them. Share lower-level UI only if the common behavior is clear.
  6. A shared component imports directly from a feature.
    Review the dependency direction; shared code depending on a feature often creates undesirable coupling.
  7. Two feature modules need each other's internals.
    Identify the shared contract/domain and expose a small public API rather than importing internal files.
  8. Imports contain long paths such as ../../../components.
    Use aliases or well-designed public entry points where they improve clarity.
  9. A barrel export creates a circular dependency.
    Inspect the dependency graph and split/restructure the public API; do not keep adding exports to the same barrel.
  10. The company wants consistent buttons, spacing and colors across products.
    Build a design system with shared tokens, components and usage guidelines.
  11. A developer puts API calls directly in every component.
    Extract reusable service/API functions or a server-state layer to separate network concerns from UI.
  12. A component has rendering, API calls, validation and business rules in 500 lines.
    Separate UI, hooks, services and domain logic based on responsibility.
  13. A team wants Atomic Design for every file.
    Explain that Atomic Design is a useful UI methodology, but forcing every component into a category can add unnecessary complexity.
  14. A design-system Button needs a feature-specific permission rule.
    Keep generic permission/business logic outside the base Button; compose it at the feature level.
  15. Five teams work on the same frontend.
    Use clear feature/module ownership, public APIs, shared design-system standards and dependency boundaries.
