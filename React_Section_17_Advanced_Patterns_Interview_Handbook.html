1. What is a React Pattern?

A pattern is a reusable way to structure components and communication. Patterns solve recurring design problems; they are not rules that every component must follow.

Problem ↓ Choose suitable pattern ↓ Reusable structure ↓ Less duplication / clearer API
Interview idea: The best pattern is usually the simplest one that solves the actual problem.

2. HOC — Higher-Order Component

A Higher-Order Component (HOC) is a function that takes a component and returns an enhanced component.

function withLoading(Component) {
  return function WithLoading({
    loading,
    ...props
  }) {
    if (loading) {
      return <p>Loading...</p>;
    }

    return <Component {...props} />;
  };
}
const UserListWithLoading =
  withLoading(UserList);

The HOC adds behavior without modifying the original component.

HOC Flow

Original Component ↓ withLoading(Component) ↓ Enhanced Component ↓ Extra behavior + Original UI

HOC — Common Uses

  • Legacy cross-cutting behavior.
  • Permission/auth checks.
  • Loading/error wrappers.
  • Analytics or instrumentation.
  • Feature flags.
In modern function-component React, custom hooks and composition often provide a simpler alternative to many HOCs.

3. Render Props

The render prop pattern passes a function as a prop. The component calls that function to decide what UI to render.

function MouseTracker({ render }) {
  const [position, setPosition] =
    useState({ x: 0, y: 0 });

  return (
    <div>
      {render(position)}
    </div>
  );
}
<MouseTracker
  render={({ x, y }) => (
    <p>
      {x}, {y}
    </p>
  )}
/>

The component owns behavior; the consumer controls presentation.

Render Props Flow

Reusable behavior ↓ Component calculates data ↓ render(data) ↓ Consumer decides UI

Render Props — Modern Alternative

function useMousePosition() {
  const [position, setPosition] =
    useState({ x: 0, y: 0 });

  // subscribe to mouse movement...

  return position;
}

function App() {
  const position = useMousePosition();

  return <p>
    {position.x}, {position.y}
  </p>;
}

Custom hooks often provide the same behavior-sharing benefit with simpler composition.

4. Compound Components

Compound components are a group of components that work together through shared state/context.

<Tabs>
  <Tabs.List>
    <Tabs.Tab value="profile">
      Profile
    </Tabs.Tab>

    <Tabs.Tab value="settings">
      Settings
    </Tabs.Tab>
  </Tabs.List>

  <Tabs.Panel value="profile">
    Profile content
  </Tabs.Panel>
</Tabs>

The API reads naturally while the parent coordinates shared state.

Compound Component Flow

Tabs ↓ Context ├── List ├── Tab └── Panel All consume shared tab state

Compound Component Example

const TabsContext =
  createContext(null);

function Tabs({ children }) {
  const [value, setValue] =
    useState("profile");

  return (
    <TabsContext.Provider
      value={{ value, setValue }}
    >
      {children}
    </TabsContext.Provider>
  );
}

function Tab({ value, children }) {
  const context =
    useContext(TabsContext);

  return (
    <button
      onClick={() =>
        context.setValue(value)
      }
    >
      {children}
    </button>
  );
}

5. Headless Components

A headless component provides behavior/accessibility/state without imposing a visual design.

Headless Component ├── state ├── behavior ├── keyboard logic └── accessibility ↓ Your UI ↓ Custom design

This is useful when you want reusable interaction logic but need complete control over appearance.

Headless Example

function useDisclosure() {
  const [open, setOpen] =
    useState(false);

  return {
    open,
    onOpen: () => setOpen(true),
    onClose: () => setOpen(false),
    onToggle: () => setOpen(v => !v)
  };
}

A design system can use this behavior with different visual components.

6. Controlled Pattern

In a controlled component, the parent owns the important state and passes the current value plus a change handler.

function Input({
  value,
  onChange
}) {
  return (
    <input
      value={value}
      onChange={e =>
        onChange(e.target.value)
      }
    />
  );
}
function App() {
  const [value, setValue] = useState("");

  return (
    <Input
      value={value}
      onChange={setValue}
    />
  );
}

Controlled Flow

Parent state ↓ value Child ↓ onChange Parent updates state ↓ New value ↓ Child

Benefit: The parent has a single source of truth and can coordinate validation, formatting and other state.

7. Uncontrolled Pattern

In an uncontrolled component, the DOM or component manages its own current value. A ref can be used to read the value when needed.

function Form() {
  const inputRef =
    useRef(null);

  function submit() {
    console.log(
      inputRef.current?.value
    );
  }

  return (
    <>
      <input ref={inputRef} />
      <button onClick={submit}>
        Submit
      </button>
    </>
  );
}

Controlled vs Uncontrolled

ControlledUncontrolled
React state owns value.DOM/component owns value.
Easy to validate/transform on each change.Can reduce state management for simple forms.
More explicit.Often simpler for basic uncontrolled inputs.
Useful for synchronized UI.Useful when React does not need every intermediate value.

8. Slot Pattern

The slot pattern lets a component accept content from the parent and place that content into defined regions.

function Card({
  header,
  footer,
  children
}) {
  return (
    <section>
      <header>{header}</header>
      <main>{children}</main>
      <footer>{footer}</footer>
    </section>
  );
}
<Card
  header={<h2>Profile</h2>}
  footer={<button>Save</button>}
>
  <p>Content</p>
</Card>

React's composition model makes slot-like APIs straightforward using props and children.

Slot Pattern — Benefit

Reusable Layout ├── header slot ├── content slot └── footer slot ↑ Parent supplies custom UI

It avoids creating many specialized components such as ProfileCard, ProductCard, OrderCard when a generic composition API is enough.

9. Provider Pattern

The Provider Pattern places shared data/behavior high in the tree so descendants can consume it without manually passing props through every level.

const AuthContext =
  createContext(null);

function App() {
  return (
    <AuthContext.Provider
      value={auth}
    >
      <Routes />
    </AuthContext.Provider>
  );
}
Provider ↓ Page ↓ Feature ↓ Button All can access shared context

Provider Pattern — Common Uses

  • Authentication/session.
  • Theme.
  • Localization.
  • Feature configuration.
  • Shared UI state.
Avoid putting every application state into one huge context. Broad context updates can cause unnecessary re-renders and make dependencies unclear.

10. Context Selector Pattern

The context selector pattern means a consumer subscribes to only the piece of context state it needs, rather than re-rendering for every context value change.

Context State ├── user ├── theme ├── notifications └── settings Consumer A → user only Consumer B → theme only Consumer C → notifications only

Plain React useContext does not provide arbitrary selector subscriptions by itself. Selector behavior can be implemented with specialized libraries or external-store patterns.

Why Context Selectors?

// Conceptual API
const user = useContextSelector(
  AppContext,
  state => state.user
);

The important idea is selective subscription, not the exact hook name. This can reduce unnecessary work in large shared state trees.

12. Patterns in Modern React

Older / Common patterns HOC Render Props ↓ Modern composition Custom Hooks Context Component composition Headless components

HOCs and render props are still valid. They are simply less common for many new React designs because hooks and composition often express the same ideas more directly.

13. Avoid Overengineering

Patterns are tools, not goals.

// If a simple component is enough:
function Button({ children }) {
  return <button>{children}</button>;
}

Do not introduce HOCs, context, compound components or generic abstractions just to make a component look "advanced".

14. Composition Over Inheritance

React commonly favors composition: build complex UI by combining smaller components and passing elements/functions as props.

function Layout({ sidebar, children }) {
  return (
    <div>
      <aside>{sidebar}</aside>
      <main>{children}</main>
    </div>
  );
}

This makes layout and behavior reusable without creating deep inheritance hierarchies.

15. Pattern Combinations

Real applications often combine patterns.

Headless behavior + Compound components + Context + Controlled / uncontrolled API ↓ Flexible component library

For example, a Tabs component can use context internally, expose compound subcomponents, and optionally support a controlled selected value.

Most Asked Interview Questions

  1. What is an HOC? A function that takes a component and returns an enhanced component.
  2. Are HOCs still used? Yes, especially in existing libraries/codebases and some cross-cutting concerns, but hooks/composition often provide simpler new designs.
  3. What is Render Props? Passing a function prop so the consumer controls the rendered UI while the component owns behavior/data.
  4. Render Props vs Custom Hook? Both can share behavior; hooks often provide simpler logic reuse while render props directly control rendering.
  5. What are Compound Components? Coordinated components that share state/context and expose a declarative API such as Tabs.Tab and Tabs.Panel.
  6. What is a Headless Component? A component/hook that provides behavior, state and often accessibility without imposing visual styling.
  7. Controlled vs uncontrolled? Controlled state is owned by React/parent props; uncontrolled state is managed internally/DOM and read when needed.
  8. When use controlled inputs? When the application needs to synchronize, validate, transform or coordinate the value continuously.
  9. When use uncontrolled inputs? When React does not need every intermediate value and a simpler DOM-owned form is appropriate.
  10. What is the Slot Pattern? Passing elements/children into named regions of a reusable component.
  11. What is the Provider Pattern? Providing shared data/behavior high in the tree for descendants to consume through context or another provider mechanism.
  12. What problem does context selector solve? It allows consumers to subscribe to selected state rather than broadly responding to unrelated context changes.
  13. Does useContext support selectors? Plain useContext reads the context value as a whole; selective subscriptions need another approach/library.
  14. Why prefer composition? It creates flexible relationships without deep inheritance and keeps responsibilities explicit.
  15. Can patterns be combined? Yes. Compound components can use context, controlled APIs and headless behavior together.
  16. What is the biggest mistake with patterns? Using a complex pattern when a simple component, hook or composition would solve the problem.

Scenario-Based Questions

  1. Several old components need the same authorization wrapper.
    A HOC can be appropriate, especially when working with an existing HOC-based architecture.
  2. You are building new shared behavior for function components.
    Consider a custom hook before creating a new HOC.
  3. A reusable component owns keyboard/state logic but each product needs different styling.
    Use a headless component or hook.
  4. You need Tabs with Tabs.List, Tabs.Tab and Tabs.Panel.
    Compound components with shared context are a natural fit.
  5. The parent needs complete control over a dialog's open state.
    Expose a controlled API such as open + onOpenChange.
  6. A simple form does not need live React state.
    Consider an uncontrolled input and read its value on submit.
  7. A Card needs custom header, body and footer content.
    Use composition/slots via props and children.
  8. Ten deeply nested components need the current theme.
    Use a Theme Provider/context rather than prop drilling.
  9. A giant context causes many components to re-render.
    Split contexts or use selective subscription/context-selector/external-store patterns where appropriate.
  10. A context contains user, theme and notifications.
    Consider separate contexts or more selective state subscriptions if consumers are unrelated.
  11. A developer wants an HOC for a tiny one-off component.
    Prefer the simplest solution; an HOC may add unnecessary indirection.
  12. A render prop creates deeply nested JSX.
    Consider replacing it with a custom hook or simpler composition if the abstraction remains clear.
  13. A headless dropdown must support keyboard navigation.
    The headless layer should own the interaction/accessibility behavior while the consumer controls presentation.
  14. A reusable component needs optional custom actions in its header.
    Expose a slot-like prop such as actions or headerContent.
  15. A component library wants both controlled and uncontrolled usage.
    Design the API carefully so controlled state has a clear source of truth and uncontrolled mode has internal state/default values.
