1. What is State Management?

State is data that changes over time and affects application behavior or UI. State management is how that data is stored, updated, shared and synchronized.

User action ↓ Update state ↓ Application reacts ↓ UI updates Different state types: Local UI state Shared client state Server state URL state Form state
Important: Not every piece of state belongs in Redux or another global store. Keep state local when possible.

2. Context API

Context lets components read a value from a provider without passing it through every intermediate component.

const ThemeContext = createContext("light");

function App() {
  return (
    <ThemeContext.Provider value="dark">
      <Dashboard />
    </ThemeContext.Provider>
  );
}

function Button() {
  const theme = useContext(ThemeContext);
  return <button>{theme}</button>;
}

Common uses include theme, locale, authentication information and other shared configuration.

Context API — Performance

When a context value changes, consumers of that context may re-render.

const value = useMemo(() => ({
  user,
  logout
}), [user, logout]);

For large or frequently changing state, consider splitting contexts or using a state-management solution with more targeted subscriptions.

3. Redux — Big Picture

Redux is a predictable state container based on a central store, actions and reducers.

UI ↓ dispatch(action) Action ↓ Middleware (optional) ↓ Reducer ↓ New Store State ↓ Subscribed UI ↓ Render

The reducer calculates the next state from the current state and an action.

Redux Store

The store holds the application's Redux state and provides APIs for reading state, dispatching actions and subscribing to changes.

const store = configureStore({
  reducer: {
    counter: counterReducer
  }
});

Modern Redux applications usually use Redux Toolkit's configureStore.

Redux Action

An action is an object describing what happened.

{
  type: "counter/increment",
  payload: 1
}

Actions should describe events or state changes rather than directly changing the store.

Redux Reducer

A reducer is a function that receives the current state and action and calculates the next state.

function counterReducer(state = { value: 0 }, action) {
  if (action.type === "increment") {
    return { value: state.value + 1 };
  }

  return state;
}

Reducers should be predictable and should not perform asynchronous side effects.

Redux Dispatch

dispatch() sends an action into the Redux update flow.

dispatch({
  type: "counter/increment",
  payload: 1
});

Middleware can intercept or transform the dispatch flow before reducers process actions.

Redux Middleware

Middleware sits between dispatch and the reducer.

dispatch(action) ↓ Middleware ↓ Reducer ↓ New state

Common uses: logging, analytics, async workflows and other cross-cutting behavior.

4. Redux Toolkit

Redux Toolkit (RTK) is the recommended way to write modern Redux logic. It reduces boilerplate and provides safer defaults.

configureStore ↓ createSlice ↓ reducers + actions ↓ dispatch ↓ store

createSlice

createSlice generates action creators and reducers from one slice definition.

const counterSlice = createSlice({
  name: "counter",
  initialState: { value: 0 },
  reducers: {
    increment(state) {
      state.value += 1;
    },
    add(state, action) {
      state.value += action.payload;
    }
  }
});

export const { increment, add } = counterSlice.actions;
export default counterSlice.reducer;

The apparent mutation is handled safely by Immer, which creates the immutable update result.

createAsyncThunk

createAsyncThunk helps represent an asynchronous operation with pending, fulfilled and rejected lifecycle actions.

export const fetchUser = createAsyncThunk(
  "user/fetchUser",
  async (userId) => {
    const response = await fetch(`/api/users/${userId}`);
    return response.json();
  }
);
extraReducers: builder => {
  builder
    .addCase(fetchUser.pending, state => {
      state.loading = true;
    })
    .addCase(fetchUser.fulfilled, (state, action) => {
      state.loading = false;
      state.data = action.payload;
    })
    .addCase(fetchUser.rejected, state => {
      state.loading = false;
    });
}

RTK Query

RTK Query is Redux Toolkit's data-fetching and server-state solution. It handles fetching, caching, subscriptions, invalidation and generated hooks.

const api = createApi({
  reducerPath: "api",
  baseQuery: fetchBaseQuery({
    baseUrl: "/api"
  }),
  endpoints: builder => ({
    getUsers: builder.query({
      query: () => "/users"
    })
  })
});

export const { useGetUsersQuery } = api;

It is often preferable to writing manual Redux reducers for API cache state.

5. Zustand

Zustand is a small client-state library based on a store and hooks. Components can subscribe to selected pieces of state.

const useCounter = create(set => ({
  count: 0,
  increment: () =>
    set(state => ({ count: state.count + 1 }))
}));

function Counter() {
  const count = useCounter(state => state.count);
  const increment = useCounter(state => state.increment);

  return (
    <button onClick={increment}>
      {count}
    </button>
  );
}

It is popular when you want simple global client state with little boilerplate.

6. MobX

MobX uses observable state and reactive tracking. Components can automatically react to observable values they read.

class Counter {
  count = 0;

  increment() {
    this.count++;
  }
}

MobX's model is more reactive and mutable-looking than Redux's action/reducer model.

Redux vs MobX

ReduxMobX
Explicit actions and reducers.Observable reactive state.
Centralized predictable update flow.Automatic tracking of observable dependencies.
Strong ecosystem and DevTools.Less boilerplate for some object-oriented/reactive models.

7. Recoil

Recoil was designed around atoms and selectors for shared React state. Atoms represent state units; selectors derive state.

const countState = atom({
  key: "count",
  default: 0
});

const count = useRecoilValue(countState);
const setCount = useSetRecoilState(countState);
Interview note: Recoil has historically been used for atom-based React state, but always check current project status before choosing a library for a new application.

8. Jotai

Jotai uses small pieces of state called atoms. Components subscribe to the atoms they use.

const countAtom = atom(0);

function Counter() {
  const [count, setCount] = useAtom(countAtom);

  return (
    <button onClick={() => setCount(c => c + 1)}>
      {count}
    </button>
  );
}

Jotai is useful when you prefer granular, atom-based state.

9. Signals

Signals are reactive values where changing a signal can notify the code that depends on it. Signals are used by several UI frameworks and libraries, with different APIs.

Signal value ↓ Reactive dependency ↓ Only affected computation/UI ↓ Update

Unlike React's standard state model, signal systems can track dependencies at a finer level. In React, signal libraries are third-party approaches rather than a built-in core state primitive.

10. Client State vs Server State

This distinction is extremely important in interviews.

Client StateServer State
Modal open/closedUsers loaded from API
Selected tabProduct list from server
ThemeCached API response
Draft UI stateData that can become stale remotely

Redux/Zustand are often used for client state. TanStack Query and RTK Query are designed for server-state/data-fetching concerns.

11. TanStack Query — Big Picture

TanStack Query manages asynchronous server state: fetching, caching, synchronization, refetching, mutations and invalidation.

Component ↓ useQuery ↓ TanStack Query Cache ↓ API ↑ Cached data / refetch / invalidation

It is not a replacement for every type of global client state. Its main strength is server data.

12. TanStack Query — Caching

const { data, isPending, error } = useQuery({
  queryKey: ["users"],
  queryFn: fetchUsers
});

The queryKey identifies the query in the cache. If another component asks for the same key, TanStack Query can reuse the cached query and coordinate subscribers.

Query Key

Query keys should include the variables that affect the result.

useQuery({
  queryKey: ["user", userId],
  queryFn: () => fetchUser(userId)
});

Different user IDs should produce different cache entries.

13. staleTime

staleTime controls how long fetched data is considered fresh.

useQuery({
  queryKey: ["products"],
  queryFn: fetchProducts,
  staleTime: 60_000
});

Here, data is considered fresh for about 60 seconds. During that period, TanStack Query does not treat it as stale simply because time passed.

Key idea: staleTime is about freshness, not how long data physically remains in memory.

14. cacheTime / gcTime

In current TanStack Query terminology, the setting is gcTime. Older versions/docs commonly called it cacheTime.

useQuery({
  queryKey: ["users"],
  queryFn: fetchUsers,
  gcTime: 5 * 60 * 1000
});

gcTime controls how long inactive cached query data can remain before garbage collection. It is different from staleTime.

staleTime vs gcTime

staleTimegcTime
How long data is considered fresh.How long inactive cached data can remain before garbage collection.
Affects freshness/refetch behavior.Affects inactive-cache lifetime.
Does not mean data is deleted after this time.Applies to inactive queries, not actively observed ones.

15. Query Invalidation

After a mutation, cached data may no longer be correct. invalidateQueries marks matching queries stale and allows them to refetch according to TanStack Query's rules.

const queryClient = useQueryClient();

queryClient.invalidateQueries({
  queryKey: ["todos"]
});
Mutation succeeds ↓ Invalidate ["todos"] ↓ Cached query becomes stale ↓ Active query can refetch ↓ UI receives fresh data

16. Mutations

useMutation is used for operations that change server data, such as create, update and delete.

const mutation = useMutation({
  mutationFn: updateUser,
  onSuccess: () => {
    queryClient.invalidateQueries({
      queryKey: ["users"]
    });
  }
});

mutation.mutate(userData);

Queries are generally for reading/fetching; mutations are for server-side changes.

17. Optimistic Updates

An optimistic update changes the UI immediately before the server confirms success.

User clicks Like ↓ Update UI immediately 👍 ↓ Send API request ↓ Success → keep change Failure → rollback
useMutation({
  mutationFn: updateTodo,
  onMutate: async newTodo => {
    await queryClient.cancelQueries({
      queryKey: ["todos"]
    });

    const previous = queryClient.getQueryData(["todos"]);

    queryClient.setQueryData(["todos"], old =>
      updateLocally(old, newTodo)
    );

    return { previous };
  },
  onError: (_error, _newTodo, context) => {
    queryClient.setQueryData(
      ["todos"],
      context.previous
    );
  },
  onSettled: () => {
    queryClient.invalidateQueries({
      queryKey: ["todos"]
    });
  }
});

The exact implementation depends on the data shape.

18. Infinite Queries

Infinite queries manage paginated data where another page can be requested as the user scrolls or clicks "Load more".

const {
  data,
  fetchNextPage,
  hasNextPage,
  isFetchingNextPage
} = useInfiniteQuery({
  queryKey: ["posts"],
  queryFn: fetchPosts,
  initialPageParam: 1,
  getNextPageParam: lastPage =>
    lastPage.nextPage ?? undefined
});

TanStack Query keeps the pages together in the query data and provides APIs for fetching the next page.

19. TanStack Query Refetching

Queries can refetch when data becomes stale and under configured triggers such as component mounting, window focus or network reconnection.

These behaviors are configurable. Do not say "TanStack Query always refetches whenever a component renders."

Most Asked Interview Questions

  1. Context vs Redux? Context is a value-sharing mechanism; Redux is a structured state-management architecture with a store, actions and reducers.
  2. What are the core Redux concepts? Store, state, actions, reducers and dispatch; middleware extends the dispatch flow.
  3. What is middleware? Logic that runs in the Redux dispatch pipeline before/around reducer processing.
  4. Why Redux Toolkit? It provides recommended defaults and utilities that reduce Redux boilerplate.
  5. What is createSlice? It defines a slice's initial state/reducers and generates action creators and the reducer.
  6. What is createAsyncThunk? A helper for async workflows that dispatches pending/fulfilled/rejected lifecycle actions.
  7. What is RTK Query? Redux Toolkit's data-fetching and caching solution for server state.
  8. Redux vs Zustand? Redux has a more structured explicit architecture; Zustand is smaller and often simpler for global client state.
  9. What is MobX? A reactive state-management library based on observable state and dependency tracking.
  10. What are atoms in Jotai/Recoil? Small independent state units that components can subscribe to.
  11. What are Signals? Reactive state primitives that track dependencies and notify affected computations/UI.
  12. What is server state? Data owned remotely that can become stale and needs fetching, caching, synchronization and invalidation.
  13. What is TanStack Query? A server-state/data-fetching library for caching, synchronization, queries and mutations.
  14. What is staleTime? How long query data is considered fresh.
  15. What is gcTime? How long inactive cached data can remain before garbage collection; older TanStack Query versions called this cacheTime.
  16. staleTime vs gcTime? Freshness vs inactive-cache lifetime.
  17. What is invalidation? Marking matching cached queries stale so they can be refetched as appropriate.
  18. What is optimistic update? Updating the UI/cache before server confirmation, with rollback on failure.
  19. What is a mutation? An operation that changes server data.
  20. What is an infinite query? A query model for loading and managing multiple pages of paginated data.

Scenario-Based Questions

  1. A theme is needed by many deeply nested components.
    Context is a natural choice.
  2. A small modal's open state is used by one component.
    Keep it local with useState rather than putting it in Redux.
  3. A large application has complex shared client state and many teams.
    Redux Toolkit can provide a predictable standardized architecture.
  4. You need a tiny global store with simple state.
    Zustand or Jotai may be a good fit depending on team preference.
  5. You need API caching and background synchronization.
    Use TanStack Query or RTK Query rather than building an API cache manually in basic Redux state.
  6. A product query should remain fresh for 60 seconds.
    Set staleTime to 60 seconds.
  7. A query is inactive and should be removed after five minutes.
    Configure gcTime appropriately.
  8. You update a todo and the list must become fresh.
    Invalidate the relevant todo query after the mutation succeeds.
  9. A like button should feel instant.
    Use an optimistic update, then rollback if the server rejects it.
  10. A user scrolls through thousands of API results.
    Use an infinite query for pagination and consider UI virtualization for rendering many rows.
  11. Two users have different IDs in the same screen.
    Include the ID in the query key, e.g. ["user", userId].
  12. A Redux reducer makes an API request.
    Do not put asynchronous side effects directly in reducers; use middleware/thunks/RTK Query or another appropriate layer.
  13. A context contains rapidly changing large application state.
    Consider splitting contexts or using a store with targeted subscriptions to reduce unnecessary consumers re-rendering.
  14. You need loading/error/success state for an API call in Redux.
    createAsyncThunk plus slice reducers can model the lifecycle, or RTK Query may be better if this is primarily server-state caching.
  15. A team asks which state library is universally best.
    Explain that the correct choice depends on state type, complexity, ecosystem, team familiarity and performance requirements.
  16. You want to reuse API data across multiple components.
    Use a server-state cache such as TanStack Query or RTK Query.
  17. A mutation succeeds but the UI still shows old cached data.
    Update the cache directly or invalidate/refetch the relevant query.
  18. Optimistic update fails.
    Rollback the previous cached state and show an error.
  19. You have an existing Redux app with many manual API reducers.
    Consider migrating suitable API-state logic to RTK Query rather than continuing to hand-build cache behavior.
  20. You need state derived from other atom values.
    Atom-based libraries can provide derived atoms/selectors depending on the library.
