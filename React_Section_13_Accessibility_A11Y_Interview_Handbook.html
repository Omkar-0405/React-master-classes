Section 13 — Accessibility (A11Y)

Simple Interview Handbook • ARIA • Keyboard Navigation • Screen Readers • Semantic HTML • Focus Management • Color Contrast

1. What is Accessibility?

Accessibility (A11Y) means building applications that people with different abilities can use effectively.

User ↓ Browser ↓ Accessibility Tree ↓ Assistive Technology ↓ Accessible experience

Accessibility benefits keyboard users, screen-reader users, people with low vision, users with motor difficulties and many others.

Best rule: Use native semantic HTML first. Add ARIA only when native HTML cannot express the required behavior.

2. Semantic HTML

Semantic elements describe the meaning of content instead of only its visual appearance.

<header>...</header>
<nav>...</nav>
<main>
  <article>...</article>
</main>
<footer>...</footer>

Semantic HTML gives browsers and assistive technologies useful structure with less custom code.

Semantic Button vs Div

<!-- Good -->
<button onClick={save}>
  Save
</button>

<!-- Usually bad -->
<div onClick={save}>
  Save
</div>

A native button already provides keyboard behavior, focus behavior and button semantics. A clickable div requires you to recreate many behaviors correctly.

3. ARIA

ARIA stands for Accessible Rich Internet Applications. It provides roles, states and properties that help assistive technologies understand custom UI.

<button
  aria-expanded={isOpen}
  aria-controls="menu"
  onClick={toggle}
>
  Menu
</button>

<div id="menu">
  ...
</div>

ARIA can describe relationships and states that are not automatically available from generic elements.

ARIA Rule of Thumb

Can native HTML express it? ↓ YES → Use native HTML ↓ NO ↓ Use appropriate ARIA + keyboard + focus behavior
Important: ARIA changes accessibility semantics; it does not automatically add keyboard behavior, focus management or interaction logic.

Common ARIA Attributes

AttributePurpose
aria-labelProvides an accessible name when visible text is not suitable.
aria-labelledbyUses another element's text as the accessible name.
aria-describedbyConnects extra descriptive/help text.
aria-expandedIndicates whether expandable content is open.
aria-controlsIdentifies content controlled by an element.
aria-hiddenHides content from the accessibility tree when appropriate.
aria-liveMarks a region where updates can be announced.

4. Keyboard Navigation

A fully accessible UI should be usable without a mouse.

Tab ↓ Interactive element ↓ Enter / Space ↓ Action Shift + Tab ↓ Move backward

Common keyboard controls include Tab, Shift + Tab, Enter, Space and Escape. Complex widgets may have additional keyboard patterns.

Keyboard Focus

button:focus-visible {
  outline: 3px solid currentColor;
  outline-offset: 2px;
}

Do not remove focus indicators without providing an equally usable replacement.

5. Screen Readers

A screen reader converts accessible information into speech or other output.

HTML ↓ Browser accessibility tree ↓ Name + role + state + value ↓ Screen reader ↓ User

Screen readers rely heavily on semantic elements, accessible names, states and relationships.

Accessible Names

<button aria-label="Close dialog">
  ✕
</button>

An icon-only button needs an accessible name. If visible text already gives the correct name, an extra aria-label may be unnecessary.

6. Focus Management

Focus management means intentionally moving or restoring keyboard focus when UI changes make that necessary.

Common cases:

  • Opening a modal.
  • Closing a modal and returning focus to its trigger.
  • Navigating to a new page/view.
  • Showing validation errors.
  • Opening menus or popovers.

Modal Focus Example

function Modal({ onClose }) {
  const closeRef = useRef(null);

  useEffect(() => {
    closeRef.current?.focus();
  }, []);

  return (
    <div role="dialog" aria-modal="true">
      <h2>Settings</h2>

      <button ref={closeRef} onClick={onClose}>
        Close
      </button>
    </div>
  );
}

A production modal should also manage focus trapping and restore focus to the element that opened it.

7. Color Contrast

Text and important UI elements need sufficient contrast so users can distinguish them.

Text ↓ Foreground color + Background color ↓ Contrast ratio ↓ Accessible / insufficient

WCAG contrast requirements depend on content and size. For normal text, a commonly referenced WCAG AA target is 4.5:1; large text commonly uses 3:1.

Do not communicate information through color alone. Combine color with text, icons, patterns or other cues when necessary.

Bad vs Better Status UI

<!-- Bad: color alone -->
<span className="red">●</span>

<!-- Better -->
<span>
  ● Error: Payment failed
</span>

The second version communicates the meaning even if the user cannot distinguish the colors.

8. Accessible Forms

<label htmlFor="email">
  Email
</label>

<input
  id="email"
  name="email"
  type="email"
  aria-describedby="email-help email-error"
/>

<p id="email-help">
  Use your work email.
</p>

<p id="email-error">
  Email is required.
</p>

Labels, descriptions and errors should be programmatically associated with the relevant field.

9. Accessible Images

<img
  src="/profile.jpg"
  alt="Priya smiling"
 />

<img
  src="/decorative-line.svg"
  alt=""
 />

Meaningful images need useful alternative text. Purely decorative images can use empty alt text so assistive technology can ignore them.

10. Headings

Use headings to create a logical document structure.

<h1>Products</h1>

<h2>Electronics</h2>
<h3>Laptops</h3>

<h2>Furniture</h2>

Do not choose heading levels only because they look visually correct. Style them separately with CSS.

11. Links vs Buttons

UsePurpose
<a> / LinkNavigate to another location.
<button>Perform an action on the current interface.
<a href="/settings">Settings</a>

<button onClick={openModal}>
  Open Settings
</button>

12. Skip Links

A skip link lets keyboard users bypass repeated navigation and jump directly to the main content.

<a className="skip-link" href="#main-content">
  Skip to main content
</a>

<main id="main-content">
  ...
</main>

It is especially useful on pages with large repeated navigation sections.

13. Live Regions

Use live regions when dynamic content needs to be announced without moving focus.

<div aria-live="polite">
  {message}
</div>

Use live announcements carefully. Too many announcements can become noisy.

14. React Accessibility

React supports normal HTML accessibility attributes, but custom components can accidentally break native behavior.

function IconButton({ label, onClick }) {
  return (
    <button
      type="button"
      aria-label={label}
      onClick={onClick}
    >
      <SaveIcon aria-hidden="true" />
    </button>
  );
}

Reusable React components should preserve semantics, keyboard behavior, labels and focus behavior.

15. Common Accessibility Mistakes

  • Using clickable div instead of buttons.
  • Removing focus outlines.
  • Missing form labels.
  • Icon-only buttons without accessible names.
  • Using color as the only error indicator.
  • Incorrect heading structure.
  • Missing image alt text.
  • Adding ARIA without implementing the required keyboard behavior.
  • Moving focus unexpectedly.
  • Building custom widgets without following established keyboard patterns.

16. Accessibility Testing

Accessibility should be tested with both automated tools and real interaction.

  • Keyboard-only navigation.
  • Screen reader testing.
  • Browser accessibility/DevTools inspection.
  • Automated checks such as axe-based tooling.
  • Color contrast testing.
  • Zoom and responsive testing.
Interview answer: Automated tools catch many common issues, but they cannot prove that an application is fully accessible.

17. A11Y Mental Model

Semantic HTML ↓ Correct name + role + state ↓ Keyboard interaction ↓ Focus management ↓ Visible focus ↓ Contrast + non-color cues ↓ Accessible experience

Most Asked Interview Questions

  1. What is A11Y? A11Y is the abbreviation commonly used for accessibility, ensuring applications can be used by people with different abilities.
  2. What is semantic HTML? HTML elements that communicate meaning and structure, such as button, nav, main, article and heading elements.
  3. What is ARIA? A set of roles, states and properties that helps communicate custom UI semantics to assistive technologies.
  4. Should ARIA replace semantic HTML? No. Prefer native semantic HTML whenever it can provide the required behavior.
  5. Does ARIA automatically make a div keyboard accessible? No. ARIA changes semantics but does not automatically implement keyboard interaction or focus behavior.
  6. Why are buttons better than clickable divs? Buttons provide built-in semantics, keyboard support and focus behavior.
  7. What is keyboard navigation? The ability to operate the interface using keyboard controls without requiring a mouse.
  8. What is focus management? Intentionally controlling/restoring keyboard focus when UI changes require it.
  9. How should a modal handle focus? Move focus into the modal, keep focus within it while appropriate, and restore focus to the triggering element when it closes.
  10. What is a screen reader? Assistive technology that presents accessible information from the browser, commonly through speech or other output.
  11. What is an accessible name? The name assistive technology uses to identify a control, often from visible text, a label or an appropriate ARIA naming mechanism.
  12. What is color contrast? The difference in luminance between foreground and background that affects readability and distinguishability.
  13. What is WCAG AA contrast for normal text? A commonly used WCAG 2.x AA target is 4.5:1 for normal text and 3:1 for large text.
  14. Why should color not be the only indicator? Users with color-vision differences or other visual limitations may not perceive the distinction.
  15. What is aria-live? It identifies a region whose dynamic updates can be announced by assistive technology.
  16. How do you make a form accessible? Use labels, correct input types, associated descriptions/errors, keyboard access and clear error feedback.
  17. How do you make an icon button accessible? Give it an accessible name, usually with visible text or an appropriate aria-label, and hide purely decorative icons from the accessibility tree.
  18. How do you test accessibility? Combine keyboard testing, screen readers, automated tools, contrast checks and browser accessibility inspection.

Scenario-Based Questions

  1. A designer made a clickable div for a Save button.
    Replace it with a semantic button unless there is a strong reason not to.
  2. A modal opens but keyboard focus stays behind it.
    Move focus into the modal and implement appropriate focus trapping/restoration.
  3. Closing a modal leaves focus at the top of the page.
    Store the trigger element and return focus to it when the modal closes.
  4. An icon-only close button has no accessible name.
    Add an accessible name such as aria-label="Close" and mark the decorative icon appropriately.
  5. A form error is shown visually but screen readers do not announce it.
    Associate the error with the input using aria-describedby and use appropriate live announcements when necessary.
  6. Keyboard users cannot reach a custom dropdown.
    Use a native select when possible; otherwise implement the correct keyboard and ARIA pattern.
  7. Focus disappears after pressing Tab.
    Inspect CSS and DOM changes; ensure focusable elements remain reachable and focus indicators are visible.
  8. A developer removed outline: none to make the design cleaner.
    Restore a visible focus indicator or provide an equally strong accessible replacement.
  9. Error messages are shown only in red.
    Add text/icon/context so the error is not communicated by color alone.
  10. A heading is styled as h1 but the page has multiple unrelated h1 elements.
    Review the document hierarchy and use headings based on structure, not appearance.
  11. An image contains important information but has alt="image".
    Replace it with concise alternative text that conveys the meaningful information.
  12. A decorative background image is announced by the screen reader.
    Ensure decorative content is excluded appropriately, for example with empty alt for decorative img elements.
  13. A success message appears after saving without moving focus.
    Consider a polite live region so the update can be announced without disrupting the user's current position.
  14. A navigation menu uses ARIA but no keyboard behavior.
    ARIA alone is insufficient; implement the interaction pattern or use a proven accessible component.
  15. An automated accessibility scan reports no errors.
    Still test keyboard and screen-reader behavior because automated tools cannot detect every accessibility problem.
