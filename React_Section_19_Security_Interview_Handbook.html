Section 19 — React Security

Simple Interview Handbook • XSS • CSRF • CSP • DOMPurify • JWT Storage • HTTPS • Secure Cookies

1. Why Web Security Matters

Frontend security is about reducing the ways an attacker can execute code, steal data, impersonate users, or abuse authenticated actions.

User Input / Network / Browser ↓ React App ↓ Security controls ├── Output escaping ├── CSP ├── Secure cookies ├── HTTPS ├── CSRF protection └── Safe data handling
Interview idea: Security is layered. No single control such as JWT, CSP or DOMPurify solves every web security problem.

2. XSS — Cross-Site Scripting

XSS happens when attacker-controlled content is interpreted as executable code in another user's browser.

Attacker-controlled input ↓ Application renders it unsafely ↓ Browser interprets attacker content ↓ Code executes in user's context

XSS can be used to manipulate pages, steal accessible data, perform actions as the user, or abuse application functionality.

3. React and XSS

React normally escapes text inserted through JSX.

const comment = userInput;

return (
  <p>{comment}</p>
);

The value is treated as text rather than being interpreted as HTML.

This protection does not mean the entire application is automatically XSS-safe. Dangerous HTML APIs, third-party libraries, URLs and DOM manipulation can still create vulnerabilities.

4. dangerouslySetInnerHTML

dangerouslySetInnerHTML tells React to insert raw HTML. It should be used only when the HTML is trusted or has been safely sanitized.

// Risky with untrusted input
<div
  dangerouslySetInnerHTML={{
    __html: userInput
  }}
/>

Never assume that "it came from the database" means it is safe. Stored attacker input can still be dangerous.

5. DOMPurify

DOMPurify is a sanitizer commonly used to remove dangerous HTML content before rendering HTML that must be accepted as input.

import DOMPurify from "dompurify";

const cleanHTML =
  DOMPurify.sanitize(untrustedHTML);

return (
  <div
    dangerouslySetInnerHTML={{
      __html: cleanHTML
    }}
  />
);
Sanitization is a defense for a specific HTML-rendering boundary. Prefer plain text rendering whenever HTML is not actually required.

6. XSS Prevention

  • Prefer normal JSX text rendering.
  • Avoid raw HTML when unnecessary.
  • Sanitize untrusted HTML before rendering.
  • Use a strong Content Security Policy.
  • Validate data at appropriate boundaries.
  • Keep dependencies updated.
  • Be careful with third-party scripts and DOM APIs.

7. CSRF — Cross-Site Request Forgery

CSRF tricks a user's browser into sending an unwanted authenticated request to a site where the user is already logged in.

User logged into bank.com ↓ Visits malicious-site.com ↓ Malicious page causes request ↓ Browser may attach bank cookies ↓ Bank receives authenticated request

CSRF is particularly relevant when authentication credentials are automatically attached by the browser, such as cookies.

8. CSRF Protection

Common defenses include:

  • SameSite cookies.
  • CSRF tokens.
  • Origin/Referer validation where appropriate.
  • Server-side request validation.
Set-Cookie:
session=...;
HttpOnly;
Secure;
SameSite=Lax

Exact cookie policy depends on the application and cross-site requirements.

9. SameSite Cookies

SettingIdea
StrictMost restrictive cross-site cookie behavior.
LaxAllows some top-level navigation use cases while restricting many cross-site requests.
NoneAllows cross-site use, but requires Secure.
SameSite is an important CSRF defense, but do not treat it as the only security control for every application.

10. CSP — Content Security Policy

CSP is a browser security policy that restricts which resources and script sources a page is allowed to use.

Content-Security-Policy:
  default-src 'self';
  script-src 'self';
  object-src 'none';

A carefully designed CSP can reduce the impact of many XSS attacks by limiting where executable content can come from.

CSP Mental Model

HTML page ↓ Browser receives CSP ↓ Browser checks resource ↓ Allowed? ── Yes → Load │ No ↓ Block / report according to policy

11. Useful CSP Directives

DirectivePurpose
default-srcFallback source policy.
script-srcControls script sources.
style-srcControls style sources.
img-srcControls image sources.
connect-srcControls fetch/XHR/WebSocket destinations.
font-srcControls font sources.
frame-srcControls embedded frames.
object-srcControls plugin/object sources.
frame-ancestorsControls which sites can embed the page.

12. JWT

JWT (JSON Web Token) is a token format commonly used to represent claims between a client and server.

Login ↓ Server authenticates user ↓ Token / session credential ↓ Client ↓ Authenticated request ↓ Server validates credential

A JWT is normally signed so the server can detect tampering. Signing does not automatically encrypt the token's contents.

13. JWT Storage

A major frontend security decision is where authentication credentials are stored.

LocationImportant tradeoff
localStorageAccessible to JavaScript, so an XSS vulnerability can expose stored tokens.
sessionStorageAlso accessible to JavaScript; typically scoped to the tab/session lifecycle.
HttpOnly cookieJavaScript cannot read it; browser sends it automatically, so CSRF protections matter.
Interview answer: There is no universal "JWT must be stored here" rule. For browser apps, HttpOnly Secure cookies are often preferred for session/refresh credentials because JavaScript cannot directly read them, while CSRF and cookie policy must be designed correctly.

14. Secure Cookies

Set-Cookie:
  session=abc;
  HttpOnly;
  Secure;
  SameSite=Lax;
  Path=/
AttributePurpose
HttpOnlyPrevents JavaScript from reading the cookie through document.cookie.
SecureSends the cookie only over HTTPS connections.
SameSiteControls cross-site cookie sending behavior.
PathLimits which URL paths receive the cookie.
Max-Age/ExpiresControls cookie lifetime.

15. HTTPS

HTTPS uses TLS to protect communication between the browser and server.

Browser ⇅ encrypted TLS connection Server Protects against: - network eavesdropping - tampering in transit - impersonation when certificate validation succeeds

HTTPS protects data in transit. It does not make an insecure application automatically safe from XSS, CSRF, broken authorization or server-side vulnerabilities.

16. HTTPS + Secure Cookie

HTTPS ↓ Encrypted transport ↓ Secure cookie ↓ Cookie sent only over HTTPS ↓ HttpOnly ↓ JavaScript cannot directly read it ↓ SameSite / CSRF controls ↓ Reduce browser-based attack surface

17. Access Token + Refresh Token

A common architecture uses a short-lived access credential and a longer-lived refresh credential.

Login ↓ Short-lived access token ↓ API requests Refresh credential ↓ Used to obtain new access token ↓ Prefer protected storage such as HttpOnly cookie

The exact architecture depends on the authentication system. Rotation, expiration and server-side revocation strategies are also important.

18. Don't Trust the Frontend

Frontend checks improve UX but are not security boundaries.

// UI check
if (user.role === "admin") {
  showDeleteButton();
}

The server must still verify authorization:

// Server
if (!currentUser.canDelete) {
  return response.status(403).end();
}
Golden rule: Authentication and authorization must ultimately be enforced server-side.

19. Security Headers

Security-related response headers can strengthen browser protections.

HeaderPurpose
Content-Security-PolicyRestricts resource/script behavior.
Strict-Transport-SecurityTells browsers to use HTTPS for the site for a specified period.
X-Content-Type-Options: nosniffReduces MIME-type sniffing behavior.
Referrer-PolicyControls referrer information sent with requests.
Permissions-PolicyControls access to selected browser capabilities.

20. Common Security Mistakes

  • Putting long-lived tokens in localStorage without understanding XSS exposure.
  • Rendering untrusted HTML directly.
  • Disabling CSP because it is inconvenient.
  • Assuming HTTPS prevents XSS.
  • Relying only on frontend role checks.
  • Using cookies without considering CSRF.
  • Logging tokens/passwords.
  • Trusting API data without validation where validation is required.
  • Using outdated dependencies with known vulnerabilities.
  • Building custom security mechanisms without understanding their threat model.

21. Security Mental Model

XSS ↓ Prevent unsafe execution ↓ Escaping + Sanitization + CSP CSRF ↓ Prevent unwanted authenticated actions ↓ SameSite + CSRF tokens + Origin checks Credential theft ↓ Protect authentication secrets ↓ HttpOnly + Secure + short lifetime + rotation Network attacks ↓ Protect data in transit ↓ HTTPS / TLS Authorization ↓ Protect resources ↓ Server-side authorization

Most Asked Interview Questions

  1. What is XSS? An attack where attacker-controlled content is executed in another user's browser context.
  2. Does React prevent XSS? React escapes normal JSX text output, but unsafe HTML APIs, URLs, DOM manipulation and dependencies can still introduce XSS risks.
  3. What is dangerouslySetInnerHTML? An API for inserting raw HTML; it must not receive untrusted unsanitized content.
  4. What is DOMPurify? A library commonly used to sanitize HTML before it is rendered as HTML.
  5. What is CSRF? An attack that causes a user's browser to make an unwanted authenticated request to a site where the user is already logged in.
  6. How do you prevent CSRF? Use appropriate SameSite cookie settings, CSRF tokens and server-side Origin/Referer validation where appropriate.
  7. What is CSP? A browser policy controlling allowed resource/script sources and reducing the impact of many injection attacks.
  8. Why is CSP useful? It creates another browser-enforced layer that can restrict where executable content can come from.
  9. Where should JWTs be stored? There is no universal answer; HttpOnly Secure cookies are often preferred for browser session/refresh credentials, while CSRF protections must be designed.
  10. Why is localStorage risky for tokens? JavaScript can read it, so an XSS vulnerability can expose tokens stored there.
  11. What does HttpOnly do? Prevents JavaScript from reading the cookie through document.cookie.
  12. What does Secure do? Restricts the cookie to HTTPS connections.
  13. What does SameSite do? Controls when cookies are sent in cross-site contexts and can reduce CSRF risk.
  14. What does HTTPS protect? It protects data in transit using TLS; it does not fix application-level vulnerabilities.
  15. Can frontend authorization checks protect an API? No. The server must enforce authorization.
  16. Does signing a JWT encrypt it? No. Signing provides integrity/authenticity of the token; the payload is not necessarily secret.
  17. What is the difference between authentication and authorization? Authentication answers who the user is; authorization answers what the user is allowed to do.
  18. What security headers should a frontend engineer know? CSP, HSTS, X-Content-Type-Options, Referrer-Policy and Permissions-Policy are common examples.

Scenario-Based Questions

  1. A user comment contains <script> and is rendered as text.
    Normal React JSX text rendering is the safer approach because React escapes the value.
  2. A product needs rich HTML comments from users.
    Sanitize the HTML with a trusted sanitizer such as DOMPurify before rendering it, and use CSP as an additional layer.
  3. A developer uses dangerouslySetInnerHTML with raw database content.
    Review the trust boundary; database content can contain stored attacker input and should be treated as untrusted unless its safety is guaranteed.
  4. A JWT is stored in localStorage and an XSS vulnerability is discovered.
    Assume the token may be exposed. Remediate the XSS, rotate/revoke credentials as appropriate and consider a safer credential-storage architecture.
  5. A session cookie is HttpOnly but a malicious site can trigger state-changing requests.
    Implement appropriate CSRF defenses such as SameSite controls and CSRF token/origin validation.
  6. A developer says HTTPS prevents XSS.
    Explain that HTTPS protects data in transit, while XSS is an application/browser execution problem.
  7. A frontend hides an admin button for normal users.
    Keep the UI check for UX, but enforce the permission on the server/API.
  8. An attacker changes role: "user" to "admin" in browser devtools.
    Never trust client-side role data for authorization; the server must derive and enforce permissions from trusted state.
  9. A CSP blocks a legitimate script.
    Review the policy and deployment model, then explicitly allow only the required trusted source/nonces/hashes rather than disabling CSP broadly.
  10. A developer suggests script-src 'unsafe-inline' everywhere.
    Explain that broad unsafe-inline weakens CSP; prefer nonces/hashes and a policy compatible with the application's architecture where feasible.
  11. A cookie contains a refresh credential.
    Use Secure and HttpOnly, choose an appropriate SameSite policy, restrict scope where possible and implement server-side expiration/rotation/revocation strategies.
  12. A log entry contains an Authorization header.
    Redact credentials from logs and audit the logging pipeline.
  13. A user can access /admin only by manually typing the URL.
    Hiding navigation is not authorization. The server must return an authorization failure for unauthorized users.
  14. A third-party script is added to the app.
    Review its trust, permissions, supply-chain risk and CSP implications; load only what is necessary and keep dependencies updated.
  15. A developer wants to build a custom token encryption scheme in JavaScript.
    Prefer established, well-reviewed authentication/security mechanisms instead of inventing cryptography.
