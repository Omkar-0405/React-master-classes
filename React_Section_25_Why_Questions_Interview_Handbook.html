Section 25 — Frequently Asked "Why?" Questions

React Interview Handbook • Understand the reason, not just the definition

How to Answer a "Why?" Question

A strong interview answer usually follows this pattern:

What? ↓ Why was it designed this way? ↓ What problem does it solve? ↓ What is the trade-off? ↓ When would you use it?
Interview tip: Do not say only "React does this for performance." Explain the actual problem, mechanism and trade-off.

1. Why Virtual DOM?

Short answer: The Virtual DOM gives React a declarative representation of UI that React can compare and use to determine efficient DOM updates.

React does not need to manually update every DOM node whenever state changes. It creates a new element tree, compares it with the previous tree, and commits the required DOM changes.

State changes ↓ New React element tree ↓ Reconciliation ↓ Required DOM changes ↓ Browser
Important: Virtual DOM is not simply "faster than the DOM." Creating/comparing virtual representations also has a cost. Its main value is enabling React's declarative rendering and reconciliation model.

2. Why Keys?

Keys give list elements stable identity so React can match elements between renders.

{items.map(item => (
  <Todo key={item.id} item={item} />
))}

Without stable identity, React may make incorrect or inefficient assumptions when items are inserted, deleted or reordered.

Remember: Key = "Which item is this?"

3. Why useMemo?

useMemo caches the result of a calculation so React can reuse it when its dependencies have not changed.

const filtered = useMemo(
  () => expensiveFilter(items, query),
  [items, query]
);

It is useful when a calculation is genuinely expensive or when a stable calculated value helps another optimization.

Do not use useMemo everywhere. It adds complexity and has its own bookkeeping cost.

4. Why useCallback?

useCallback can preserve a function reference between renders.

const handleSave = useCallback(() => {
  save(id);
}, [id]);

This can matter when passing callbacks to memoized children or when a stable function reference is required by another optimization.

Key distinction: useMemo caches a value; useCallback caches a function reference.

5. Why Can Context Cause Re-renders?

Consumers of a context can re-render when the provider's context value changes.

<ThemeContext.Provider
  value={{ theme, setTheme }}
>
  {children}
</ThemeContext.Provider>

If the value object is recreated on every provider render, consumers may see a new value identity even when the underlying data has not meaningfully changed.

const value = useMemo(
  () => ({ theme, setTheme }),
  [theme]
);

But memoizing the value is not a universal fix; component structure and context boundaries matter more.

6. Why Is React Declarative?

Declarative UI describes what the UI should look like for a given state, rather than manually describing every DOM operation.

{isLoggedIn
  ? <Dashboard />
  : <Login />}

React decides how to transition the actual DOM toward that desired UI.

Imperative "Find button → change text → hide panel" Declarative "Given state X → render UI X"

7. Why Is Reconciliation Often Described as O(n)?

React uses practical heuristics and assumptions instead of comparing every possible pair of nodes.

  • Different element types generally produce different subtrees.
  • Keys help identify children across renders.
  • React compares corresponding positions/identified children rather than solving a general tree-edit problem.

This allows reconciliation to be approximately linear for typical React tree updates, rather than using an expensive general-purpose tree transformation algorithm.

The O(n) description is a high-level model of React's reconciliation strategy, not a guarantee that every render performs exactly n operations.

8. Why React Fiber?

Fiber gives React a unit-of-work architecture that allows rendering work to be scheduled, paused, resumed and prioritized.

Large rendering work ↓ Fiber units of work ├── Work A ├── Work B ├── Work C └── Work D ↓ Scheduler can prioritize work ↓ Commit completed changes

This architecture is important for modern concurrent rendering and keeping the UI responsive during expensive rendering work.

9. Why Batching?

Batching groups multiple state updates so React can avoid unnecessary intermediate renders.

setCount(c => c + 1);
setName("Omkar");
setOpen(false);

React can process these updates together rather than rendering after every individual update.

React 18: Automatic batching was expanded to many asynchronous contexts, not just traditional React event handlers.

10. Why Immutable State?

Immutable updates make state changes predictable and allow React and related tools to reason about changed references.

// Good
setUser(prev => ({
  ...prev,
  name: "Omkar"
}));

// Avoid
user.name = "Omkar";
setUser(user);

Direct mutation can keep the same object reference and make change detection, debugging and predictable rendering harder.

11. Why Functional Updates?

Use a functional updater when the next state depends on the previous state.

setCount(prev => prev + 1);
setCount(prev => prev + 1);

This tells React exactly how each update depends on the latest queued state.

Rule: If you need previous state → prefer the updater function.

12. Why Cleanup in useEffect?

Cleanup prevents effects from leaving behind subscriptions, timers, listeners or in-flight work that is no longer needed.

useEffect(() => {
  const id = setInterval(refresh, 5000);

  return () => clearInterval(id);
}, []);
Effect starts ↓ Timer / listener / request ↓ Component unmounts or deps change ↓ Cleanup ↓ Old work removed

13. Why Does useRef Not Trigger a Re-render?

Updating ref.current changes a mutable object property; it does not schedule a React state update.

const countRef = useRef(0);

countRef.current += 1;
// Component does not re-render

This makes refs useful for values that must persist across renders but do not themselves determine what React should display.

14. Why Are State Updates Often Described as Asynchronous?

Calling a state setter does not immediately mutate the current render's state variable. React schedules the update and may batch it with other updates.

console.log(count);

setCount(count + 1);

console.log(count);
// Still the value from this render

The important idea is not that every state update is literally asynchronous like a Promise. It is that state is a snapshot for a render, and updates schedule a future render.

15. Why Does React.memo Sometimes Not Work?

React.memo compares props by reference/value rules. New object, array or function references can make props appear changed.

<Child
  data={{ id: 1 }}
  onClick={() => save()}
/>

Both props create new references when the parent renders.

const data = useMemo(
  () => ({ id: 1 }),
  []
);

const onClick = useCallback(
  () => save(),
  []
);
Do not add useMemo/useCallback automatically. First verify that the child re-render is actually expensive.

16. Why Shouldn't Index Be Used as a Key?

An array index describes an item's position, not its identity. When items are inserted, deleted or reordered, positions change.

Before 0 → A 1 → B 2 → C Insert X at start Index keys 0 → X 1 → A 2 → B Identity changed by position

This can cause component state or DOM state to be associated with the wrong item.

Use a stable item ID whenever the list can change.

17. Why Does StrictMode Render Twice in Development?

React StrictMode intentionally performs extra development-only checks to help reveal unsafe side effects and code that is not resilient to remounting.

You may observe extra rendering/effect setup-cleanup behavior in development. This does not mean production runs the application twice in the same way.

If StrictMode exposes a bug, fix the underlying side-effect/lifecycle problem instead of trying to hide the extra development behavior.

18. Why Is Derived State Usually an Anti-pattern?

If a value can be calculated from existing props/state, storing another copy creates two sources of truth.

const [firstName, setFirstName] = useState("");
const [lastName, setLastName] = useState("");

// Usually unnecessary:
const [fullName, setFullName] = useState("");

Instead:

const fullName =
  `${firstName} ${lastName}`.trim();

Now fullName cannot become stale relative to firstName/lastName.

19. Why React Query Instead of Redux for Server State?

Server state has different problems from ordinary client state: fetching, caching, stale data, retries, invalidation, mutations and synchronization.

ReduxReact Query / TanStack Query
Excellent for client/application state.Designed around server-state fetching and caching.
You build more fetching/cache patterns yourself unless using additional tools.Provides query caching, invalidation, mutations and async state patterns.
This is not "Redux is bad." Redux Toolkit can manage client state very well, and RTK Query is specifically designed for data fetching/caching.

20. Why Does Suspense Improve UX?

Suspense lets React coordinate a loading boundary and show fallback UI while certain content is not ready.

<Suspense fallback={<PageSkeleton />}>
  <Reports />
</Suspense>
Request / lazy component ↓ Not ready ↓ Suspense boundary ↓ Fallback UI ↓ Content ready ↓ Real UI

Good boundaries let users see useful parts of the application instead of waiting for one large screen to be ready.

21. Why Does Concurrent Rendering Matter?

Concurrent rendering lets React work on rendering without requiring every update to block the browser until the entire render is completed.

React can prioritize urgent interactions and schedule less urgent rendering work differently.

startTransition(() => {
  setSearchResults(results);
});

This is especially useful when a non-urgent update is expensive and should not make typing or clicking feel blocked.

Concurrent rendering is about React's rendering model and scheduling. It does not mean JavaScript becomes multithreaded.

Most Asked Interview Follow-ups

  1. Is Virtual DOM always faster than direct DOM manipulation?
    No. Direct targeted DOM operations can be faster in some cases. React's advantage is a consistent declarative model and reconciliation strategy.
  2. Can keys be random values?
    No. Random keys change identity on every render and can cause unnecessary remounts.
  3. When should you avoid useMemo?
    When the calculation is cheap or memoization does not prevent meaningful work.
  4. Does useCallback stop a function from being recreated internally?
    Think of it primarily as preserving the function value/reference returned across renders when dependencies are unchanged; the optimization matters when identity affects downstream work.
  5. Does Context always re-render the whole application?
    No. Context updates affect consumers of that context; component structure and subscriptions determine the actual rendering impact.
  6. Why not manipulate the DOM directly?
    Direct DOM manipulation can conflict with React's declarative ownership. Refs are the appropriate escape hatch for specific imperative operations.
  7. Does reconciliation compare every node with every other node?
    No. React uses heuristics, element types and keys to make the practical comparison efficient.
  8. Is Fiber a separate renderer?
    Fiber is React's internal architecture for representing work and enabling scheduling/prioritization.
  9. Can batching change observable behavior?
    Yes, code should not assume a state setter immediately changes the current render's value.
  10. Why is mutation dangerous?
    It can preserve object identity and make updates harder to detect and reason about.
  11. When should I use a functional updater?
    When the new value depends on the previous value, especially with multiple queued updates.
  12. Does useEffect cleanup run only on unmount?
    No. Cleanup also runs before the effect re-runs after dependency changes.
  13. Can refs replace state?
    No. If a value affects rendered output, it generally belongs in state.
  14. Why does console.log show old state after setState?
    The current render's state is a snapshot; the setter schedules a new render.
  15. Why can React.memo fail to skip a child?
    Props may contain new object/function references or the component may have its own state/context changes.
  16. Why is index key acceptable sometimes?
    For a truly static list that never reorders, inserts or deletes, index keys can be acceptable, but stable IDs are safer when identity can change.
  17. Does StrictMode double-render production?
    The extra development checks are development-only behavior.
  18. Is all derived state bad?
    No. The issue is storing data that can be cheaply derived from existing state/props and then maintaining two sources of truth.
  19. Is React Query a replacement for Redux?
    Not exactly. They solve different categories of state; React Query focuses on server state, while Redux is a general client-state architecture.
  20. Does Suspense fetch data automatically?
    Suspense is a rendering/loading coordination mechanism. Whether it triggers data fetching depends on the framework/library integration.
  21. Does concurrent rendering use multiple JavaScript threads?
    No. It allows React to schedule rendering work more flexibly; JavaScript execution still follows the platform's execution model.

Scenario-Based Questions

  1. A list loses input values after sorting.
    Check the keys. If indexes are used, sorting changes identity by position. Use stable item IDs.
  2. A memoized child still renders whenever the parent renders.
    Inspect its props for new object/array/function references and check whether context or local state is causing the render.
  3. A component calculates a large filtered dataset on every render.
    Profile it. If the calculation is genuinely expensive, use useMemo with correct dependencies or improve the underlying algorithm.
  4. A context provider causes many unrelated components to render.
    Split context boundaries, reduce the provider value's changing surface and keep unrelated state out of the same context.
  5. Three setCount(count + 1) calls produce only one increment.
    All three updates use the same render snapshot. Use functional updates: setCount(c => c + 1).
  6. A WebSocket keeps receiving messages after navigation.
    Clean up the subscription in useEffect so the old connection/listener is removed.
  7. A component needs the latest value inside a timer without re-rendering.
    Consider storing the latest value in a ref, while keeping displayed state in state if the UI must update.
  8. Derived fullName becomes stale.
    Remove duplicated state and derive it from firstName/lastName during rendering.
  9. A React.memo optimization makes code much more complicated but performance barely changes.
    Remove unnecessary memoization and optimize only measured bottlenecks.
  10. A developer sees effects run twice after enabling StrictMode.
    Explain the development-only checks and verify that effects have correct setup/cleanup behavior.
  11. A large rendering update makes typing feel laggy.
    Separate urgent input state from non-urgent rendering work and consider startTransition/useDeferredValue where appropriate.
  12. A dashboard waits for one slow widget before showing anything.
    Use independent loading boundaries/data fetching so unrelated sections can render while the slow section loads.
  13. A team stores every API response in Redux.
    Consider a server-state solution such as RTK Query or TanStack Query for caching, invalidation and synchronization concerns.
  14. A developer says "Virtual DOM makes all DOM updates faster."
    Correct the oversimplification: React's value is the declarative reconciliation architecture; performance depends on the workload and implementation.
  15. A component mutates an object and calls setState with the same object.
    Use an immutable update that creates the required new object references.
