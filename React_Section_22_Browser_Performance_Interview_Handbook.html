Section 22 — Browser Performance

Simple Interview Handbook • Lighthouse • Core Web Vitals • LCP • CLS • INP • Lazy Loading • Image Optimization • Bundle Analysis

1. What is Web Performance?

Web performance is how quickly and smoothly a user can load, see, interact with and use a website.

User opens page ↓ HTML / CSS / JS / Images ↓ Browser processes resources ↓ Page becomes visible ↓ User interacts ↓ Browser responds
Interview idea: Performance is not only bundle size. Network latency, rendering, images, JavaScript execution, layout shifts and interaction responsiveness all matter.

2. Lighthouse

Lighthouse is a tool that audits web pages and provides performance-related diagnostics along with other categories such as accessibility and SEO.

Lighthouse ↓ Page audit ├── Performance ├── Accessibility ├── Best Practices └── SEO ↓ Scores + diagnostics ↓ Optimization opportunities

Use Lighthouse to find opportunities, then validate improvements with real-user data where possible.

3. Lighthouse — How to Use It

  1. Open Chrome DevTools.
  2. Open the Lighthouse panel.
  3. Choose the page/device conditions.
  4. Run the audit.
  5. Inspect metrics and diagnostics.
  6. Fix high-impact issues.
  7. Measure again.
A Lighthouse score is a lab measurement, not a complete picture of real users. Network/device conditions and test variability can affect results.

4. Core Web Vitals

Core Web Vitals are Google's user-experience metrics focused on loading, visual stability and responsiveness.

MetricMeasures
LCPLoading performance.
CLSVisual stability.
INPInteraction responsiveness.

5. LCP — Largest Contentful Paint

LCP measures when the largest relevant content element visible in the viewport is rendered.

Navigation ↓ HTML arrives ↓ CSS / fonts / images load ↓ Largest visible content appears ↓ LCP

Common LCP elements include a large image, poster image, heading or block of text.

LCP Targets

ResultLCP
Good≤ 2.5 seconds
Needs improvement> 2.5s and ≤ 4.0s
Poor> 4.0s

These thresholds are evaluated at the 75th percentile for real-user Core Web Vitals assessment.

6. How to Improve LCP

  • Improve server response time.
  • Prioritize the LCP resource.
  • Optimize the hero image.
  • Use responsive image sizes.
  • Reduce render-blocking resources.
  • Reduce unnecessary JavaScript.
  • Preload truly critical resources when appropriate.
  • Use a CDN where useful.

7. CLS — Cumulative Layout Shift

CLS measures unexpected visual movement of page content during loading.

Page starts ↓ Text appears ↓ Image has no reserved space ↓ Image loads ↓ Content moves ↓ Layout shift ❌

Example: a button moves just as the user tries to click it because an image above it suddenly appears.

CLS Targets

ResultCLS
Good≤ 0.1
Needs improvement> 0.1 and ≤ 0.25
Poor> 0.25

8. How to Reduce CLS

  • Set width/height or aspect ratio for images and videos.
  • Reserve space for dynamic content.
  • Avoid inserting content above existing content unexpectedly.
  • Use stable font-loading strategies.
  • Animate with properties that do not cause unnecessary layout changes.
<img
  src="/hero.webp"
  width="1200"
  height="600"
  alt="Hero"
/>

The browser can reserve the image's space before it loads.

9. INP — Interaction to Next Paint

INP measures interaction responsiveness by looking at how quickly the page responds visually after user interactions during the visit.

User click / tap / key press ↓ Event handler ↓ JavaScript work ↓ Rendering ↓ Next visual update ↓ INP

Long JavaScript tasks can delay the browser from responding to user input.

INP Targets

ResultINP
Good≤ 200 ms
Needs improvement> 200ms and ≤ 500ms
Poor> 500ms

10. How to Improve INP

  • Break up long JavaScript tasks.
  • Reduce unnecessary re-renders.
  • Virtualize very large lists.
  • Defer non-critical work.
  • Use memoization when it actually helps.
  • Move heavy computation off the main thread when appropriate.
  • Keep event handlers lightweight.

11. Core Web Vitals Mental Model

LCP ↓ "How fast did the main content appear?" CLS ↓ "Did the page stay visually stable?" INP ↓ "How quickly did the page respond to interaction?"

12. Lazy Loading

Lazy loading delays loading a resource until it is likely to be needed.

const Reports =
  lazy(() => import("./Reports"));

<Suspense fallback={<Spinner />}>
  <Reports />
</Suspense>

Here the Reports code can be loaded when that part of the application is needed.

Lazy Loading — Good Candidates

  • Large routes.
  • Rarely used features.
  • Heavy editors.
  • Charts or reporting screens.
  • Admin-only functionality.
  • Below-the-fold images when appropriate.
Do not lazy-load everything. Critical above-the-fold content should usually remain immediately available.

13. Image Optimization

Images can be one of the largest contributors to page weight.

Original image ↓ Choose correct dimensions ↓ Compress ↓ Modern format ↓ Responsive source ↓ Lazy-load if non-critical ↓ Browser

14. Image Techniques

  • Use appropriately sized images.
  • Prefer modern formats such as WebP/AVIF when supported.
  • Use responsive images.
  • Compress images.
  • Reserve dimensions to reduce CLS.
  • Lazy-load non-critical images.
  • Do not lazy-load the main LCP image by default.
<img
  src="/product-800.webp"
  srcSet="
    /product-400.webp 400w,
    /product-800.webp 800w,
    /product-1200.webp 1200w"
  sizes="(max-width: 600px) 100vw, 50vw"
  width="1200"
  height="800"
  alt="Product"
/>

15. Image Priority

ImageTypical strategy
Hero/LCP imagePrioritize appropriately; avoid unnecessary lazy loading.
Below-the-fold imageLazy-load when beneficial.
Small iconUse an efficient asset or SVG where appropriate.
Large galleryResponsive sizing + lazy loading + optimized formats.

16. Bundle Analysis

Bundle analysis shows what contributes to JavaScript bundle size.

Production bundle ↓ Bundle analyzer ├── React ├── UI library ├── chart library ├── date library └── application code ↓ Find large dependencies ↓ Optimize

17. Why Bundle Analysis?

A bundle may be large because of:

  • Heavy dependencies.
  • Duplicate packages.
  • Unused modules.
  • Large icon imports.
  • Large chart/editor libraries.
  • Application code loaded too early.

Bundle analysis turns "the app is slow" into measurable candidates for optimization.

18. Bundle Optimization Example

// Potentially broad import
import * as Icons from "large-icon-library";

// Prefer a targeted import when supported
import { Search } from "large-icon-library";

The exact effect depends on the library's module format and bundler tree-shaking behavior. Measure the resulting bundle rather than assuming.

19. Browser Main Thread

The browser's main thread handles important work including JavaScript execution, style/layout and painting. Long tasks can delay interaction and rendering.

Main Thread ├── JavaScript ├── Style calculation ├── Layout ├── Paint └── Event handling Long JS task ↓ Browser cannot respond quickly ↓ Poor INP / jank

20. React Performance Connection

ProblemPossible React solution
Unnecessary re-rendersState colocation, memoization where justified.
Huge listVirtualization.
Heavy initial JSCode splitting/lazy loading.
Expensive computationOptimize algorithm / memoize when useful / move work off main thread when appropriate.
Large imagesResponsive images + compression + correct loading priority.

21. Performance Investigation Flow

User reports "slow" ↓ Reproduce ↓ Measure ├── Lighthouse ├── DevTools Performance ├── Network ├── Core Web Vitals └── Bundle analyzer ↓ Find bottleneck ↓ Optimize ↓ Measure again
Golden rule: Measure before and after. Performance optimization without measurement is often guesswork.

Most Asked Interview Questions

  1. What is Lighthouse? A web auditing tool that provides performance diagnostics and other audits such as accessibility and SEO.
  2. What are Core Web Vitals? User-experience metrics focused on loading, visual stability and responsiveness: LCP, CLS and INP.
  3. What is LCP? Largest Contentful Paint measures when the largest relevant visible content element is rendered.
  4. What is a good LCP? At the 75th percentile, ≤ 2.5 seconds is considered good.
  5. What is CLS? Cumulative Layout Shift measures unexpected visual layout movement.
  6. What is a good CLS? At the 75th percentile, ≤ 0.1 is considered good.
  7. What is INP? Interaction to Next Paint measures responsiveness to user interactions across a page visit.
  8. What is a good INP? At the 75th percentile, ≤ 200 ms is considered good.
  9. How do you improve LCP? Improve server response, prioritize the LCP resource, optimize images, reduce blocking resources and reduce unnecessary JS.
  10. How do you reduce CLS? Reserve space for media/dynamic content and avoid unexpected insertion/layout changes.
  11. How do you improve INP? Reduce long tasks, unnecessary renders and heavy event-handler work.
  12. What is lazy loading? Loading a resource when it is likely to be needed instead of immediately.
  13. Should the LCP image be lazy-loaded? Usually not; the main LCP resource generally needs priority rather than being delayed.
  14. How do you optimize images? Use correct dimensions, responsive sources, compression, modern formats and appropriate loading priority.
  15. What is bundle analysis? Inspecting bundle contents and sizes to identify large or unnecessary dependencies.
  16. Why is bundle size important? More JavaScript can increase download, parse, compile and execution work, especially on slower devices/networks.
  17. Does a high Lighthouse score guarantee a fast app? No. It is a lab audit; real-user conditions and runtime behavior also matter.
  18. How do you approach a performance problem? Measure, identify the bottleneck, make a targeted change, then measure again.

Scenario-Based Questions

  1. LCP is 5 seconds because of a large hero image.
    Resize/compress the image, use an efficient format and responsive source, ensure it is not unnecessarily lazy-loaded, and prioritize its loading.
  2. Users click a button but it reacts slowly.
    Profile the interaction, look for long main-thread tasks and reduce/block less JavaScript work.
  3. CLS is high because images push content downward.
    Reserve image dimensions using width/height or aspect ratio.
  4. A dashboard loads a 2 MB charting library before the user opens Reports.
    Split/lazy-load the Reports feature so the heavy library is not part of the initial path when it is not needed.
  5. The page has excellent Lighthouse scores but real users report slowness.
    Check real-user metrics, device/network distributions and production behavior; lab conditions may not represent users.
  6. A page loads 30 below-the-fold images immediately.
    Use lazy loading and responsive image sizes where appropriate.
  7. Mobile users have poor INP after opening a large table.
    Virtualize the table, reduce rendering work and avoid expensive synchronous handlers.
  8. A 3000-row table makes scrolling slow.
    Use list/table virtualization so only visible rows need rendering.
  9. A bundle analyzer shows a huge dependency used for one tiny feature.
    Consider a lighter library, targeted import or lazy-loading that feature.
  10. A developer wants to memoize every component.
    Do not blindly memoize. Profile first and use memoization where it prevents meaningful repeated work.
  11. Images are small on desktop but huge on mobile.
    Use responsive images so the browser can choose a suitable source for the viewport.
  12. Text moves when a web font loads.
    Review font loading and fallback metrics; aim to minimize layout shifts and avoid unexpected content movement.
  13. A lazy-loaded route shows a blank screen for several seconds.
    Provide a meaningful Suspense fallback and investigate chunk size/network/loading bottlenecks.
  14. The developer says reducing bundle size will fix every performance issue.
    Explain that performance is broader: server response, images, rendering, main-thread work, layout and interactions all matter.
  15. A performance optimization makes the bundle smaller but interaction slower.
    Measure the actual user impact; optimize for overall experience rather than one metric in isolation.
