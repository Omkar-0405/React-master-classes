Section 18 — React Error Handling

Simple Interview Handbook • Error Boundaries • Suspense • Fallback UI • Retry UI • Logging

1. Why Error Handling?

Error handling prevents one failure from making the whole user experience unusable and gives users a clear recovery path.

Error ↓ Detect ↓ Contain ↓ Show useful UI ↓ Log / report ↓ Recover or retry
Interview idea: Error handling has two goals: protect the user experience and give developers enough information to diagnose the problem.

2. Error Boundary

An Error Boundary is a React component that catches rendering errors in its descendant tree and displays fallback UI instead of letting the broken subtree take down the whole interface.

Error boundaries are implemented using class components with static getDerivedStateFromError and/or componentDidCatch, or through framework/library abstractions built on them.

class ErrorBoundary
  extends React.Component {

  state = {
    hasError: false
  };

  static getDerivedStateFromError() {
    return { hasError: true };
  }

  componentDidCatch(error, info) {
    console.error(error, info);
  }

  render() {
    if (this.state.hasError) {
      return <p>Something went wrong.</p>;
    }

    return this.props.children;
  }
}

Error Boundary Flow

App ↓ Error Boundary ↓ Feature ↓ Component ❌ ↓ Boundary catches render error ↓ Fallback UI

The boundary can isolate a part of the application instead of showing a broken screen everywhere.

3. What Error Boundaries Catch

Error boundaries catch errors during rendering and certain React lifecycle/constructor work in their descendant tree.

  • Rendering errors.
  • Errors in class lifecycle methods.
  • Errors in constructors of descendant components.
Important: Error boundaries do not automatically catch every kind of error. Event-handler errors, asynchronous callback errors and server-side rendering errors need their own handling strategies.

4. Event Handler Errors

function Button() {
  function handleClick() {
    try {
      riskyOperation();
    } catch (error) {
      console.error(error);
    }
  }

  return (
    <button onClick={handleClick}>
      Save
    </button>
  );
}

Use normal JavaScript try/catch for errors that occur directly in event handlers.

5. Async/API Errors

async function loadUsers() {
  try {
    const response =
      await fetch("/api/users");

    if (!response.ok) {
      throw new Error(
        `HTTP ${response.status}`
      );
    }

    return await response.json();
  } catch (error) {
    setError(error);
  }
}

Network failures and API errors should normally be handled at the data-fetching layer and represented in the UI with loading/error states.

6. Fallback UI

Fallback UI is the interface shown when the expected content cannot currently be displayed.

Normal UI ↓ Failure ↓ Fallback ├── Explain problem ├── Keep useful navigation └── Offer recovery

Good fallback UI is specific, calm and actionable.

Good vs Bad Fallback

WeakBetter
"Error.""We couldn't load your orders."
No recovery.Retry button.
Blank page.Preserve surrounding navigation.
Technical stack trace.Useful user-friendly message.

7. Retry UI

A retry action lets the user repeat an operation that may fail temporarily.

function UserList() {
  const [error, setError] =
    useState(null);

  async function load() {
    try {
      setError(null);
      // fetch data...
    } catch (e) {
      setError(e);
    }
  }

  if (error) {
    return (
      <div>
        <p>Could not load users.</p>
        <button onClick={load}>
          Try again
        </button>
      </div>
    );
  }

  return <UserTable />;
}

Retry Strategy

Request ↓ Failure? ├── No → Show data └── Yes ↓ Transient error? ├── Yes → Retry └── No → Explain / fix action

Do not retry every error forever. Authentication errors, validation errors and permanent failures usually need a different response.

8. Automatic Retry vs Manual Retry

AutomaticManual
Useful for transient network failures.Useful when user action is needed.
Must have retry limits/backoff.Clear to the user.
Can recover silently.Good for important failed operations.

9. Suspense

React Suspense lets a part of the UI show a fallback while a supported child operation is not ready.

<Suspense
  fallback={<Spinner />}
>
  <LazyPage />
</Suspense>

Common use cases include lazy-loaded components and framework-supported data/code loading.

Suspense Flow

Render ↓ Child not ready ↓ Suspense boundary ↓ Fallback UI ↓ Child becomes ready ↓ Real UI
Suspense is primarily a loading/readiness mechanism. It is not a replacement for Error Boundaries.

10. Suspense + Lazy Loading

import { lazy, Suspense } from "react";

const Dashboard = lazy(
  () => import("./Dashboard")
);

function App() {
  return (
    <Suspense
      fallback={<p>Loading...</p>}
    >
      <Dashboard />
    </Suspense>
  );
}

The dynamic import creates a separately loaded chunk, while Suspense provides the loading UI while it is unavailable.

11. Suspense vs Error Boundary

SuspenseError Boundary
Handles "not ready yet".Handles certain descendant errors.
Shows fallback while waiting.Shows fallback after an error.
Often used with lazy loading.Used to isolate rendering failures.
Loading/readiness concept.Error/recovery concept.

12. Combining Suspense and Error Boundary

<ErrorBoundary>
  <Suspense fallback={<Spinner />}>
    <Dashboard />
  </Suspense>
</ErrorBoundary>
Error Boundary ↓ Suspense ↙ ↘ Loading Error ↓ ↓ Fallback Error UI ↓ Success UI

13. Logging

Logging records useful diagnostic information so developers can understand what failed.

componentDidCatch(error, info) {
  logger.error({
    error,
    componentStack: info.componentStack
  });
}

In production, logs are often sent to an error-monitoring platform rather than only printed to the browser console.

What Should You Log?

  • Error message/type.
  • Stack trace.
  • React component stack when available.
  • Route/page.
  • Relevant non-sensitive context.
  • Application version/build.
  • Useful request/correlation ID.
Security: Never log passwords, access tokens, session secrets or unnecessary personal/sensitive data.

14. Logging Levels

LevelUse
DebugDetailed development diagnostics.
InfoUseful application events.
WarnUnexpected condition that is not necessarily a failure.
ErrorFailure requiring investigation or recovery.

15. Error Classification

Error ├── User / Validation │ → Explain + correct input │ ├── Authentication │ → Re-authenticate │ ├── Authorization │ → Explain permission issue │ ├── Network / Transient │ → Retry / reconnect │ ├── Server │ → Fallback + retry │ └── Programming / Render → Error Boundary + log

Classification helps choose the correct recovery instead of showing the same generic message for every failure.

16. Error Boundary with Retry

class ErrorBoundary
  extends React.Component {

  state = {
    hasError: false
  };

  static getDerivedStateFromError() {
    return { hasError: true };
  }

  reset = () => {
    this.setState({ hasError: false });
  };

  render() {
    if (this.state.hasError) {
      return (
        <div>
          <p>Something went wrong.</p>
          <button onClick={this.reset}>
            Try again
          </button>
        </div>
      );
    }

    return this.props.children;
  }
}

In real applications, retrying may also require resetting failed data/query state or changing a boundary key so the failed subtree is genuinely remounted.

17. Boundary Placement

App ├── Header ├── Error Boundary │ └── Dashboard │ ├── Chart │ └── Table └── Footer

Place boundaries around meaningful sections. One global boundary is useful as a last-resort safety net, while smaller boundaries can isolate independent features.

18. Common Mistakes

  • Showing a blank screen after an error.
  • Using one generic message for every failure.
  • Retrying permanent errors indefinitely.
  • Assuming Error Boundaries catch event-handler errors.
  • Using Suspense as if it were an error handler.
  • Logging sensitive data.
  • Logging only "Something went wrong" with no diagnostic context.
  • Putting one boundary around everything and losing feature isolation.
  • Giving users a retry button that cannot actually reset the failed state.

19. Production Error Strategy

User action ↓ Application ↓ Error occurs ↓ Classify ├── Recover locally ├── Retry ├── Show fallback └── Ask user for action ↓ Log safely ↓ Monitoring / alerting ↓ Developer fixes

Most Asked Interview Questions

  1. What is an Error Boundary? A React component that catches certain descendant rendering/lifecycle errors and displays fallback UI.
  2. Can a functional component itself be an Error Boundary? React's built-in Error Boundary mechanism is class-based; functional components commonly consume boundaries provided by a wrapper/library/framework.
  3. What does getDerivedStateFromError do? It updates state so the boundary can render fallback UI after an error.
  4. What does componentDidCatch do? It provides a place to perform side effects such as logging the error and component stack.
  5. What errors do Error Boundaries not catch? They do not automatically catch event-handler errors, many asynchronous callback errors, or errors outside their descendant render/lifecycle scope.
  6. What is Suspense? A mechanism for showing fallback UI while supported child content is not ready.
  7. Is Suspense an Error Boundary? No. Suspense handles waiting/readiness; Error Boundaries handle certain errors.
  8. Where is Suspense commonly used? Lazy-loaded components and framework-supported loading/data patterns.
  9. What is fallback UI? The UI shown when normal content cannot currently be displayed or is still loading.
  10. What makes good fallback UI? Clear explanation, preserved navigation where possible, useful recovery and no unnecessary technical details.
  11. When should you retry an API request? Mainly for transient failures, with sensible limits and backoff for automatic retries.
  12. Why not retry every error? Validation, permission and other permanent errors will not be fixed by repeated requests.
  13. What should production logging contain? Useful error/context information such as stack, route, version and correlation data, while excluding secrets and unnecessary sensitive data.
  14. Why use multiple Error Boundaries? To isolate independent parts of the UI so one failure does not necessarily break the entire application.
  15. How do you retry after an Error Boundary failure? Reset the boundary/subtree and also reset any relevant failed state or data source.
  16. How do you handle fetch errors? Check the response, throw/represent failures, catch them at the data layer and expose loading/error/retry states to the UI.
  17. What is the difference between loading and error states? Loading means work is still in progress; error means the operation failed and needs recovery or user action.
  18. Should you show stack traces to users? No. Show a useful user-facing message and keep detailed diagnostics in protected logs.

Scenario-Based Questions

  1. A chart crashes and the whole dashboard disappears.
    Wrap the chart/dashboard section in an Error Boundary so the failure is isolated and provide a useful fallback.
  2. A button's click handler throws.
    Handle the error inside the event flow with try/catch or an appropriate action error state; do not rely on an Error Boundary to catch it.
  3. A lazy-loaded page fails to render.
    Use Suspense for the loading state and an Error Boundary around the lazy subtree for failures.
  4. An API request returns 500.
    Represent the request as an error state, show a useful message and offer retry when retrying makes sense.
  5. The network temporarily disconnects.
    Consider bounded automatic retry with backoff or a clear manual retry action.
  6. The API returns 400 because the form is invalid.
    Do not blindly retry. Show the validation error and let the user correct the input.
  7. A request fails because the session expired.
    Handle authentication separately, such as refreshing/re-authenticating or redirecting appropriately.
  8. A retry button does nothing because cached failed state remains.
    Reset the relevant query/request state or remount/reset the failed subtree before retrying.
  9. The product team wants one "Something went wrong" message everywhere.
    Use a consistent design but classify errors so users receive useful, context-specific recovery actions.
  10. Production logs contain access tokens.
    Remove/redact secrets immediately and audit logging so sensitive credentials are never recorded.
  11. A developer adds console.error everywhere.
    Centralize production error reporting where practical and attach useful context rather than scattering unstructured logs.
  12. A global Error Boundary catches everything.
    Keep it as a last-resort safety net but add smaller boundaries around independently useful application sections.
  13. A Suspense fallback shows forever.
    Investigate the underlying loading/data/code path; Suspense itself does not mean the operation failed.
  14. A component fails because of a programming bug.
    Contain it with an Error Boundary, log diagnostic details, show fallback UI and fix the underlying bug.
  15. An error message exposes database details to users.
    Return a safe user-facing message and keep detailed technical diagnostics in protected logs.
