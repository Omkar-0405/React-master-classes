1. Why Do We Test?

Testing gives confidence that software behaves correctly and continues to behave correctly after changes.

Code change ↓ Run tests ↓ Pass → confidence Fail → investigate ↓ Fix / improve

Good tests focus on important behavior rather than implementation details.

Interview idea: A strong test suite usually has many focused unit/component tests, fewer integration tests, and a smaller number of critical E2E tests.

2. Testing Pyramid

/\ /E2E\ /------\ / Integr.\ /----------\ / Unit/Comp. \ /--------------\ More tests → lower layers Fewer tests → expensive upper layers

This is a useful mental model, not a strict rule. Modern teams may use different testing distributions depending on the product.

3. Jest

Jest is a JavaScript testing framework with test runners, assertions, mocking utilities and coverage support.

function add(a, b) {
  return a + b;
}

test("adds two numbers", () => {
  expect(add(2, 3)).toBe(5);
});

Jest can test JavaScript logic and can be used with React projects alongside a UI testing library.

Jest — Common Matchers

expect(value).toBe(10);

expect(obj).toEqual({
  id: 1,
  name: "Omkar"
});

expect(items).toContain("React");

expect(result).toBeTruthy();
expect(result).toBeFalsy();

expect(fn).toHaveBeenCalled();

expect(() => risky()).toThrow();

toBe is generally for exact/primitive equality; toEqual compares object/array contents.

4. React Testing Library

React Testing Library (RTL) encourages testing React components the way users interact with them.

import {
  render,
  screen
} from "@testing-library/react";

test("shows heading", () => {
  render(<Welcome name="Omkar" />);

  expect(
    screen.getByRole("heading", {
      name: /welcome/i
    })
  ).toBeInTheDocument();
});
Core philosophy: Prefer accessible/user-facing queries over selectors tied to implementation details.

5. RTL Queries

QueryTypical use
getByRolePreferred for accessible interactive/UI elements.
getByLabelTextForm controls with labels.
getByTextVisible text.
getByPlaceholderTextWhen placeholder is the useful available identifier.
getByTestIdFallback when a suitable user-facing query is not available.

get vs query vs find

QueryBehavior
getBy...Returns immediately; throws if not found.
queryBy...Returns null if not found; useful for asserting absence.
findBy...Returns a Promise and waits for an async element to appear.
expect(
  screen.queryByText("Error")
).not.toBeInTheDocument();

const user = await screen.findByText("Omkar");

6. User Interactions

Use user-event for realistic user interactions when possible.

import userEvent from "@testing-library/user-event";

test("user can type email", async () => {
  const user = userEvent.setup();

  render(<Login />);

  await user.type(
    screen.getByLabelText(/email/i),
    "a@example.com"
  );

  expect(
    screen.getByDisplayValue("a@example.com")
  ).toBeInTheDocument();
});

7. Mocking

Mocking replaces a real dependency with controlled test behavior.

Component ↓ Real API ❌ ↓ Mock API / Mock function ↓ Predictable test

Mocking is useful for network requests, timers, modules, functions and external services.

Jest Function Mock

const onSave = jest.fn();

render(<Form onSave={onSave} />);

await user.click(
  screen.getByRole("button", { name: /save/i })
);

expect(onSave).toHaveBeenCalledTimes(1);

8. Mocking API Requests

For UI tests, a network-mocking tool such as Mock Service Worker (MSW) can intercept requests while allowing the application to use its normal API code.

server.use(
  http.get("/api/users", () => {
    return HttpResponse.json([
      { id: 1, name: "Omkar" }
    ]);
  })
);

This avoids tightly coupling component tests to a particular HTTP client implementation.

9. Snapshot Testing

Snapshot testing stores a serialized representation of output and compares future test runs against it.

expect(container.firstChild)
  .toMatchSnapshot();

If output changes, the snapshot test fails until the difference is reviewed.

Important: Do not blindly update snapshots. A passing snapshot only means the output matches the stored snapshot, not that the UI is correct.

Snapshot Testing — Pros & Cons

ProsCons
Quick way to detect unexpected output changes.Large snapshots can become noisy.
Useful for stable serialized structures.Developers may update snapshots without reviewing behavior.
Can document expected structure.Often less behavior-focused than user-oriented tests.

10. Unit Testing

A unit test focuses on a small piece of logic in isolation.

function calculateTotal(price, tax) {
  return price + price * tax;
}

test("calculates total", () => {
  expect(calculateTotal(100, 0.1))
    .toBe(110);
});

Unit tests are fast and useful for pure functions, reducers, utilities and business logic.

11. Component Testing

A component test checks a React component's rendered behavior, interaction and state changes.

test("increments count", async () => {
  const user = userEvent.setup();

  render(<Counter />);

  await user.click(
    screen.getByRole("button", {
      name: /increment/i
    })
  );

  expect(
    screen.getByText("1")
  ).toBeInTheDocument();
});

12. Integration Testing

Integration tests verify that multiple pieces work together.

Login Component + Form Validation + API Mock + Auth State ↓ Integration Test ↓ Expected user behavior

Example: render a login form, type credentials, submit, mock the API response and verify that the user sees the authenticated UI.

Unit vs Integration

UnitIntegration
Small isolated behavior.Multiple parts working together.
Fast.Usually slower.
Mocks more dependencies when needed.Often uses fewer internal mocks.
Great for pure logic.Great for realistic application flows within the frontend.

13. E2E Testing

End-to-end (E2E) tests verify an application through a real browser-like flow, often across frontend and backend boundaries.

Browser ↓ React App ↓ API ↓ Database / services ↓ Real user flow

E2E tests are powerful but generally slower and more expensive to maintain than unit/component tests.

14. Cypress

Cypress is a browser-based testing framework commonly used for E2E and component testing.

describe("login", () => {
  it("logs in", () => {
    cy.visit("/login");

    cy.get("[name=email]")
      .type("user@example.com");

    cy.get("[name=password]")
      .type("secret");

    cy.contains("button", "Login")
      .click();

    cy.url()
      .should("include", "/dashboard");
  });
});

Cypress provides automatic waiting, browser tooling and an interactive runner.

15. Playwright

Playwright is a browser automation/testing framework with support for Chromium, Firefox and WebKit.

import { test, expect } from "@playwright/test";

test("user can log in", async ({ page }) => {
  await page.goto("/login");

  await page.getByLabel("Email")
    .fill("user@example.com");

  await page.getByLabel("Password")
    .fill("secret");

  await page.getByRole("button", {
    name: "Login"
  }).click();

  await expect(page).toHaveURL(/dashboard/);
});

Cypress vs Playwright

CypressPlaywright
Strong interactive developer experience.Strong cross-browser automation.
Runs closely with the browser/application.Automates browser contexts through Playwright APIs.
Popular for component/E2E testing.Popular for E2E and multi-browser testing.
Different architecture and tradeoffs.Supports Chromium, Firefox and WebKit.

Choose based on team needs and project architecture rather than assuming one is universally better.

17. Testing Async UI

test("loads user", async () => {
  render(<User />);

  expect(
    screen.getByText(/loading/i)
  ).toBeInTheDocument();

  expect(
    await screen.findByText("Omkar")
  ).toBeInTheDocument();
});

For async UI, wait for observable behavior rather than adding arbitrary delays.

18. What Should You Test?

  • Important user-visible behavior.
  • Business rules.
  • Critical interactions.
  • Error and loading states.
  • Authentication/authorization flows.
  • Regression-prone areas.
  • Important edge cases.
Avoid testing implementation details such as private component state when the same behavior can be verified through the UI.

19. Good Test Example

// Behavior-focused
test("shows validation error for empty email", async () => {
  const user = userEvent.setup();

  render(<LoginForm />);

  await user.click(
    screen.getByRole("button", { name: /login/i })
  );

  expect(
    screen.getByText("Email is required")
  ).toBeInTheDocument();
});

The test describes what the user experiences rather than how the component internally stores the error.

20. Test Independence

Tests should normally be independent so the result of one test does not depend on another test's execution order.

beforeEach(() => {
  // reset mocks/state/test data
});

afterEach(() => {
  // cleanup resources
});

Shared mutable state is a common cause of flaky tests.

21. Flaky Tests

A flaky test sometimes passes and sometimes fails without a relevant code change.

  • Waiting for arbitrary timeouts.
  • Race conditions.
  • Shared test state.
  • Unstable external services.
  • Non-deterministic data.
  • Incorrect async handling.
Fix: Wait for real conditions, isolate state, control dependencies and make test data deterministic.

Most Asked Interview Questions

  1. What is Jest? A JavaScript testing framework with a runner, assertions, mocking and coverage features.
  2. What is React Testing Library? A UI testing library focused on testing React behavior through user-facing interactions and accessible queries.
  3. Why use getByRole? It encourages tests based on accessible semantics and how users/assistive technology identify elements.
  4. getBy vs queryBy vs findBy? get throws immediately if missing, query returns null if missing, find waits asynchronously for the element.
  5. What is mocking? Replacing a dependency with controlled behavior for a test.
  6. What is a snapshot test? A test that compares serialized output with a stored snapshot.
  7. What is unit testing? Testing a small piece of logic in isolation.
  8. What is integration testing? Testing multiple parts working together.
  9. What is E2E testing? Testing a complete user flow through a browser and application stack.
  10. Cypress vs Playwright? Both support browser testing; Cypress emphasizes its interactive browser-based experience, while Playwright provides broad cross-browser automation including Chromium, Firefox and WebKit.
  11. Should every component have a snapshot? No. Prefer meaningful behavior tests; use snapshots selectively.
  12. Should implementation details be tested? Usually no; test observable behavior.
  13. How do you test API calls? Mock/intercept network behavior and verify UI behavior rather than relying on live external services.
  14. What is MSW? A tool that intercepts network requests and returns controlled responses for tests.
  15. How do you test async components? Use async queries such as findBy or waitFor around observable state changes.
  16. What causes flaky tests? Timing assumptions, shared state, race conditions, unstable dependencies and incorrect async handling.
  17. Why should tests be independent? So order and parallel execution do not change the result.
  18. What is test coverage? A measurement of which code/branches/statements are exercised by tests; high coverage does not automatically mean high-quality tests.

Scenario-Based Questions

  1. A button works only when a specific internal state variable changes.
    Prefer testing the user action and resulting UI rather than inspecting that state variable directly.
  2. An API test fails when the internet is unavailable.
    Mock/intercept the network so the test is deterministic and does not depend on external services.
  3. A component shows loading, then data.
    Assert the loading state and await the data using findBy/waitFor based on the actual behavior.
  4. getByText fails because the element is split across nested elements.
    Use a more appropriate semantic query such as getByRole or a carefully chosen text/function matcher.
  5. You need to assert that an error is absent.
    Use queryBy and assert that the result is null/not in the document.
  6. A test passes locally but fails in CI because of timing.
    Remove arbitrary sleeps, wait for actual conditions and investigate race conditions/environment differences.
  7. Ten tests modify the same global mock.
    Reset/restore mocks between tests and avoid shared mutable state.
  8. A snapshot changed because a CSS class changed.
    Review whether the change affects behavior; do not automatically update the snapshot.
  9. A 100-line snapshot changes every week.
    Prefer smaller behavior-focused assertions that verify meaningful user-visible outcomes.
  10. You need to test a pure currency calculation.
    Write a unit test with several normal and edge cases.
  11. You need to test login form + API + auth state.
    Use an integration-style test with mocked network behavior.
  12. You need to verify a real checkout flow.
    Use a focused E2E test because the flow spans multiple application layers.
  13. You need to test the same checkout flow in multiple browsers.
    Playwright is a strong option because it supports Chromium, Firefox and WebKit.
  14. A team wants E2E tests for every tiny utility.
    Explain that unit tests are cheaper and faster for isolated logic; reserve E2E for important cross-system user journeys.
  15. A test clicks a div with onClick.
    Consider whether the production component should be a button; test accessible behavior rather than preserving an inaccessible implementation.
